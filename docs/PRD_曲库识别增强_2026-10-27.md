# PRD：ERAVJ 曲库扫描与识别增强

> 文档类型：简单 PRD（用户已给明确需求，不做竞品/市场分析）
> 文档日期：2026-10-27
> 涉及项目：ERAVJ（`P:\ERAVJ\AutoVJ`，演出端）、ERALIB（`P:\ERAVJ\ERLIB_曲库分析`，曲库分析工具）、ERCUE（`P:\ERAVJ\EasyRealityCue`，DJ 码表编排工具）

## 项目信息

- 语言：中文
- 原始需求复述（逐字，不扩大不缩水）：
  1. 曲库扫描功能增强（ERAVJ 与 ERALIB 中均实现）：BPM 分析、波形图生成；右键歌曲打开详情页；可手动标记 BPM、手动标记多个八拍起点、对同一首歌分段标记不同的 BPM。
  2. 分段 BPM / 八拍起点要对着波形图标记（在波形上点选/拖拽）。
  3. 先验证指纹识别精准度（本地 + B站），确认无误后再做实时识别（流程门槛）。
  4. ERAVJ 正在演出中的实时歌曲识别，并做 BPM 对齐 + 八拍起点对齐，用于精确定位素材自动切换的起点。
  5. 修复实时音频分析两个 bug：BPM 被错误减半；Hardstyle/Hardcore 在 Drop 段落能量分析偏低。

## 1. 产品目标

在不破坏现有「离线建库 → 演出查表」架构的前提下，把曲库扫描从「指纹 + 节拍网格 + 曲风 + 封面」升级为「可人工校对的完整歌曲识别档案」：让 DJ 在建库端（ERAVJ/ERALIB）看到波形、手动订正 BPM 与八拍起点、按段落拆分 BPM，产出演出端（ERAVJ）在实时识别时可直接消费的精确对齐信息，从而把素材自动切换的起点从「大概对拍」提升到「精确落在八拍头」，并先修复当前 BPM 减半与 Hardstyle/Hardcore Drop 能量偏低两个实时分析 bug 作为可靠性的前提。

## 2. 用户故事

- 作为 VJ，我在演出中放一首已建库的歌，希望系统实时认出这首歌并把 BPM 与八拍起点对齐到这首录音的真实位置，这样素材切换能稳定落在八拍头上，而不是每次都差半拍。
- 作为 VJ，我扫描曲库后右键一首歌打开详情页，能一边看波形一边把自动 BPM 识别错的歌手动改成正确 BPM，并确认它确实生效到演出端的对齐结果。
- 作为 VJ，我遇到一首「前半段 128、后半段 155」的变速歌，希望在波形上拖选两段、分别标 BPM，让演出端在跨过变速点时仍能对齐八拍头。
- 作为 DJ，我在曲库里给一首 Hardcore 手动点出多个八拍起点，希望导出到演出端后，实时识别能优先用我标记的这些点来定位自动切换起点。
- 作为 QA/DJ，我在把实时识别正式上线前，先用本地曲库和 B 站现场音频验证指纹识别的命中率与位置精度，确认无误后才让实时识别 + 对齐功能上线。

## 3. 需求池

> 优先级：P0=必须（含流程门槛），P1=应做（依赖 P0 验证通过），P2=可做。

### P0

- **P0-1 指纹识别精准度验证（流程门槛）**：在本地曲库与 B 站现场音频两类样本上跑通「指纹命中率 + 位置偏移（秒/拍）」的量化验证，产出可复现的验证报告与通过阈值；在验证确认无误前，实时识别（P1）不进入实装。*验收：报告给出命中率、位置误差分布、失败样本清单，阈值经 QA 与架构师签字确认。*
- **P0-2 曲库扫描 BPM 分析落地展示（ERAVJ + ERALIB）**：把已有 `beatgrid.py` 的离线 BPM/锚点/八拍相位结果在曲库列表与详情页中展示出来（含来源 `src` 与置信度 `conf`），不新造 BPM 算法。*验收：扫描后每首歌能看到 BPM 值与来源（vdj/bt/local），无 BPM 的歌曲有明确占位与原因。*
- **P0-3 波形图生成（ERAVJ + ERALIB）**：扫描时为每首歌生成波形图（峰值包络/缩略图），用于详情页展示与人工标记。*验收：每首歌扫描后可在详情页看到与音频时长对齐的波形，生成失败不阻断扫描且显示原因。*
- **P0-4 右键歌曲打开详情页（ERAVJ + ERALIB）**：曲库列表右键/双击一首歌打开只读+可编辑的详情页。*验收：详情页展示元数据、封面、BPM、波形、八拍起点/分段列表，ERAVJ 与 ERALIB 交互一致。*
- **P0-5 手动标记 BPM（ERAVJ + ERALIB）**：在详情页手动录入/覆盖单曲 BPM，标记为「手动」来源并覆盖自动值。*验收：手动 BPM 保存后详情页与演出端对齐结果均采用手动值，可回退到自动值。*
- **P0-6 手动标记多个八拍起点（ERAVJ + ERALIB）**：在波形上点选/拖拽标记多个八拍起点（垂直标记线），支持增删改。*验收：可标记≥2 个八拍起点，导出/保存后演出端能读取并按「最近的八拍头」对齐。*
- **P0-7 分段标记不同 BPM（ERAVJ + ERALIB）**：对同一首歌在波形上拖选区间、为每段单独标 BPM，段与段首尾相接。*验收：一首歌可存≥2 个 BPM 分段，各段有独立 BPM 与八拍起点，跨段时演出端能切到对应段的 BPM。*
- **P0-8 修复 BPM 被错误减半（ERAVJ）**：定位 `audio_engine.py` BPM 估计 v6 中「kick 梳状优先 + 半速修正」导致真值被估成 1/2 的路径并修复，回归 B 站/本地已知样本。*验收：问题样本（如 128/160/180 BPM 曲）实时 BPM 稳定显示真值，不再出现 64/80/90 的减半值，且不影响已锁定的正常歌。*
- **P0-9 修复 Hardstyle/Hardcore Drop 能量偏低（ERAVJ）**：针对 Hardstyle/Hardcore 类 Drop 段（低频冲击强但非全曲峰值、响度被压平）能量打分偏低的路径修复。*验收：已知样本（如 `Alcohol Duper -Hardstyle VIP-` 3:03~3:29）Drop 段能量达到与鼓点段匹配的水平，且不抬高钢琴/人声 breakdown 段。*

### P1

- **P1-1 实时歌曲识别（ERAVJ，依赖 P0-1 通过）**：演出中实时识别正在播放的歌曲（复用 `fp.FingerprintDB.match` + 码表指纹灌库链）。*验收：本地曲库/码表包歌曲在混播/变速/搓碟场景下能持续识别出正确 song_id，换歌能及时切换。*
- **P1-2 BPM 对齐（ERAVJ，依赖 P0-1）**：实时识别锁定歌曲后，用其离线网格（或分段/手动订正值）对齐实时 BPM，用于拍钟与切换节奏。*验收：锁定后拍钟按该曲 BPM 推进，变速（±8% 内）能跟随，不再依赖实时 BPM 估计的偶发飞值。*
- **P1-3 八拍起点对齐（ERAVJ，依赖 P0-1）**：实时识别后把「素材自动切换起点」对齐到该曲的八拍头（`anchor + 8n×beat_len`，多八拍/分段时取当前段最近的八拍头）。*验收：自动切换发生在八拍头，实测误差 ≤ 半个八拍（阈值待 QA 定），多八拍起点/分段 BPM 均生效。*

### P2

- **P2-1 波形标记吸附增强**：标记八拍起点/BPM 分段时提供「吸附到拍/小节」与缩放、undo/redo 的精细编辑。*验收：标记操作可吸附、可撤销，不阻塞 P0 主流程。*
- **P2-2 批量人工校对**：曲库列表支持批量查看/批量标 BPM 的快速校对流。*验收：可多选快速改 BPM，效率高于逐首进详情页。*
- **P2-3 识别结果 HUD 展示**：演出端 HUD 显示「当前识别歌曲 + BPM + 对齐状态 + 下一八拍倒计时」。*验收：HUD 可读、低干扰、可关闭。*

## 4. UI 设计

### 4.1 详情页（曲库 → 右键/双击一首歌）

布局为左右分栏，参考 ERAVJ 码表页 `cue_page.CueDetailPanel` 的「左列表 / 右详情」交互，ERALIB 在 `app.py` 主列表同款复用。

```
┌─ 详情页（歌曲详情）─────────────────────────────────────────┐
│ 顶栏：封面缩略图 | 曲名/艺人/时长/曲风 | [自动BPM] [手动BPM输入] │
│ ┌─────────────────────────────┬───────────────────────────┐ │
│ │ 波形视图（主区）             │ 信息面板（右侧）           │ │
│ │  · 横轴=时间秒，纵轴=幅度     │  · BPM 当前值/来源/置信度   │ │
│ │  · 八拍起点=垂直标记线(可拖动)│  · 分段 BPM 列表（可增删）  │ │
│ │  · BPM 分段=不同底色带+分隔线 │  · 八拍起点列表（可增删）   │ │
│ │  · 工具栏：[选择][标八拍]     │  · 保存/回退自动 按钮        │ │
│ │            [标分段][播放试听] │                           │ │
│ └─────────────────────────────┴───────────────────────────┘ │
│ 底部：状态提示（已存 N 个八拍起点 / N 个 BPM 分段 / 是否有未保存修改）│
└──────────────────────────────────────────────────────────────┘
```

### 4.2 波形标记交互（核心）

- **波形**：复用 ERCUE 已验证的 `timeline_widget.py` 波形绘制思路（峰值包络 + 时间轴），详情页内以「只读波形 + 可叠加标记」的方式呈现；波形数据来自扫描时生成的波形图/峰值数组。
- **手动 BPM**：顶部「BPM」数字框直接输入；或工具栏「标 BPM」后在波形某点单击，以该点所在的拍周期推算并回填。手动后来源显示「手动」，可用「回退自动」撤销。
- **手动多个八拍起点**：工具栏切到「标八拍」模式 → 在波形上单击/拖拽打一个垂直标记线，即为一个八拍头；可拖动调整、右键删除。多个标记线共存，分别表示 `anchor_i`。
- **分段 BPM（关键交互说明）**：
  1. 工具栏切到「标分段」模式；
  2. 在波形上**拖拽框选一个时间区间**（起点=上一段终点或 0，终点=松开位置），弹出该段 BPM 输入框；
  3. 确认后生成一个分段：`{t0_sec, bpm, beat_len=60/bpm, anchor=该段第一个八拍头}`；
  4. 分段以不同底色/分隔线在波形上显示，相邻段自动首尾相接（后一段 `t0` = 前一段终点），整曲必须被分段连续覆盖；
  5. 点选某分段可改 BPM 或删除（删除后与相邻段合并）。
- **保存**：详情页改动先落「本地歌曲档案」，再通过现有导出链路（ERALIB `.eravjlib` / ERAVJ `music_meta`）进入演出端消费。

## 5. 数据模型草案

> 现状确认：单曲网格现在统一为 `grid` dict（`beatgrid.py` 输出，字段 `bpm/beat_len/anchor/phrase/contrast/src/conf/dur/peaks/grid_ver/remix/vdj_bpm/vdj_delta`），`anchor` 为**单个**八拍头（八拍头 = `anchor + 8n×beat_len`）。`.ercue` 的 `tracks[].identity` 目前只有 `bpm`（码表时间轴坐标系）、无 anchor。以下为**草案**，字段命名与兼容策略由架构师最终裁定。

### 5.1 手动 BPM（`bpm_manual`）

- 存储位置：`grid` dict 内新增 `bpm_manual`（float，`0`/缺省 = 未手动）+ `src="manual"` 标记；手动生效时 `bpm = bpm_manual` 覆盖自动值。
- 落库文件/字段：
  - ERALIB `.eravjlib`：`songs.grid`（JSON，`format.LibWriter.add_song` 透传）新增 `bpm_manual`、`src`。
  - ERAVJ 本地：`config.json` → `music_meta[path]["grid"]` 新增 `bpm_manual`、`src`（与 `store_grid`/`get_grid` 同路径）。
  - ERCUE `.ercue`：`tracks[].identity.bpm` 已是码表时间轴 BPM；若手动订正，编排端改写该 `bpm`（不影响 `fp_id`/`file_md5` 认歌链）。

### 5.2 多个八拍起点（`anchors`）

- 存储位置：`grid` dict 内把单值 `anchor` 扩展为 `anchors`（有序 float 列表，秒）；保留 `anchor = anchors[0]` 作向后兼容。
- 落库文件/字段：
  - ERALIB `.eravjlib`：`songs.grid["anchors"]`（JSON）。
  - ERAVJ 本地：`music_meta[path]["grid"]["anchors"]`。
- 消费语义：演出端「八拍起点对齐」取当前 offset 附近最近的 `anchor_i`，再按 `anchor_i + 8n×beat_len` 推下一个八拍头（改造 `beatgrid.grid_anchor_after` / `GridClock` 的取锚逻辑，默认仍可用单 `anchor`）。

### 5.3 分段 BPM（`segments`）

- 存储位置：`grid` dict 内新增 `segments`：`[{t0_sec, bpm, beat_len, anchor}, ...]`，按 `t0_sec` 升序、首尾相接覆盖全曲；单段时等价于现有单 `grid`（`segments` 缺省 = 整曲一段）。
- 落库文件/字段：
  - ERALIB `.eravjlib`：`songs.grid["segments"]`（JSON）。
  - ERAVJ 本地：`music_meta[path]["grid"]["segments"]`。
- 消费语义：演出端按当前 offset 查所属段，取该段 `bpm`/`beat_len`/`anchor` 做 BPM 对齐与八拍头对齐；跨段时无缝切到下一段（`GridClock`/拍钟需支持「段内 grid」而非整曲单 grid）。

### 5.4 波形图（`waveform`）

- 草案（二选一，待架构师定）：
  - ERALIB `.eravjlib` 新增 `waveforms` 表（`song_id` + 峰值数组 JSON 或 PNG BLOB），与 `covers` 表同构；`format.py`/`scanner.py` 各加读写。
  - ERAVJ 本地扫描落 `thumbs/` 同级 `waveforms/` 目录（PNG/峰值 JSON），详情页按需加载。
- 原则：波形是「人工标记的载体」，必须与音频时长严格对齐；生成失败不阻断扫描。

### 5.5 兼容性

- 老 `grid`（无 `anchors`/`segments`/`bpm_manual`）读取时全部按「单段、单八拍、自动 BPM」退化，行为逐值不变；新字段**不**因此升 `GRID_VER`/`FORMAT_VERSION`（除非消费语义改变），由架构师最终裁定。

## 6. 待确认问题（供架构师裁定）

1. **分段 BPM 与 `.ercue` 的关系**：`.ercue` `identity` 目前只存单 `bpm`，不存 anchor/分段。分段 BPM/多八拍起点是否要回写到 `.ercue`，还是只存在 ERAVJ/ERALIB 的歌曲档案里、由演出端识别后单独取用？（现状码表 `at_sec` 是秒权威、不依赖 BPM，需确认分段 BPM 是否影响码表触发。）
2. **多八拍起点与分段 BPM 的优先级/共存规则**：一首歌同时有「多八拍起点」和「分段 BPM」时，某段的 `anchor` 与该段外的手动八拍点冲突如何裁决（段内 anchor 优先？还是全局合并去重？）。
3. **波形图的存储形态与体积**：峰值数组 JSON vs PNG，以及大曲库（千首级）下的磁盘/内存成本与懒加载策略。
4. **BPM 减半修复是否触及 `GRID_VER`/指纹版本**：`audio_engine.py` 实时 BPM 估计改动是否影响 `beatgrid.py` 离线结果与已建库网格，是否需要增量重算。
5. **实时识别验证阈值的口径**：本地与 B 站两类的「命中率 / 位置误差 / 变速容差」通过线各取多少，由谁签字。
6. **详情页在 ERAVJ 的落位**：是加进现有音乐库面板（`ui_main` 曲库/素材库），还是参照码表页独立成页；右键入口与既有右键菜单（打标签/播放/移除）如何合并。
7. **波形标记的吸附精度**：八拍起点/BPM 分段标记是否需要「吸附到拍/小节」以及缩放级别（P2 的吸附是必做还是可后置）。
8. **ERAVJ 与 ERALIB 详情页代码复用边界**：两个仓库无法互相 import，波形/标记控件是抽公共模块还是各维护一份（参照 `fp.py`↔`fp_core.py` 的「逐字节一致」双实现纪律）。
