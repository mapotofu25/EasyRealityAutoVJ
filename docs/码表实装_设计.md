## 0. 一页纸结论

- **做什么**：把 `.ercue`（DJ 端 EasyRealityCue 导出的码表包）导入演出端，挂到一个**「码表图层」**上；运行时用**指纹认歌**定位到"歌内第几拍"，按码表把每层的"当前片段/画面变换/混合/淡入淡出"渲染出来。**DJ 手动选素材的那套自动调度在码表接管期间让位**（用户原话：码表里是 DJ 做好的成片）。
- **不做什么**：不做编排界面（无 `cue_editor.py`/`cue_preview.py`/第 3 页签）；不做设备位置源（VirtualDJ OSC）——**只用指纹**；不做码表的"新建/编辑/保存"。
- **落地方式 = 融合移植**：从 `pre_strip_bak` 里把 **数据模型 + 运行时解释器 + 引擎的码表分支 + UI 的导入/绑定入口** 挑回来，**只挑片段，绝不整体覆盖**（当前文件比备份晚一个月、多 4k+ 行）。
- **两端对齐的 6 条契约**（见 §2.4）是硬约束：几何 cover/contain、fade=α²、能力表、内嵌素材幂等解压、`src_out` 冻结、位置=指纹。
- **性能红线**：渲染热路径只做"读已算好的 `cs_states` + `player.current()` + `_draw_layer`"；**重活（认歌/解码/预加载）全部移出热路径**；每帧额外成本目标 **< 1% fps 退化**（用现有 fps A/B 基准量）。
- **风险 top3**：①当前 `_draw_layer` **没有 crop 参数**（旧版有，须补，且是热路径函数）；②码表解码器**激活/回收**若漏掉会复现"12 核 CPU / 磁盘 750MB/s"历史事故；③指纹定位的**相位/拍长**若与 Cue 端不一致 ⇒ 整条码表错位（两端必须用同一 `bpm`/beat_len）。

## ① 预期用途（用户明确要求"先说明"）

### 1.1 码表在演出时解决什么问题
- **DJ 预先精编排**：DJ 在 EasyRealityCue 里给"某一首特定曲子"逐段排好"第几拍上什么画面、怎么摆/怎么混/怎么进出"，存成 `.ercue`。
- **演出时按拍精确执行**：现场放到这首歌时，演出端**自动**按码表在正确的拍点上切画面，不需要 DJ 现场手点。
- **与"曲库/素材库自动调度"的关系**：演出端本来有一套"按曲风/能量/节拍自动轮播素材"的调度（`_auto_switch_tick` / `_switch_layer_random`）。**码表是"这首曲子我全权指定"的覆盖层** —— 码表图层接管期间，该图层的自动调度停用，改由码表驱动；**没有绑定码表 / 没认到歌 / 码表图层不可见** 时，立刻退回普通自动调度（安全降级，绝不黑屏）。

### 1.2 什么时候用
- 对"这首曲子的视觉有明确设计要求"的场合（主打曲、有设计的 drop、要卡点）。
- 其余曲子继续用自动调度，**两者共存**：码表只在"认到歌 + 有码表 + 图层可见"时生效。

### 1.3 本次**明确不做**的（附理由）
- **不做编排界面**：编排整套（时间轴/预览/拖动）已在 EasyRealityCue 里，重复造会重演"码表把主程序拖垮"的历史（README 原话："所有的问题都是码表加上后导致"）。**单一职责**：Cue 端负责编排，演出端负责执行。
- **不做设备位置源（VirtualDJ OSC 等）**：`position_source.py` 已被删；且用户 2026-09-29 明确"**位置以指纹为准，这一版不接设备**"。指纹链（`fp.py` 304 行 / `charge_engine.py` 250 行）**当前仍在**，直接复用。**延后**设备源（真需要时再加，且仍作为"指纹给不出"时的后备）。
- **不做码表的编辑/另存**：演出端只读 `.ercue`。

## ② 数据来源

### 2.1 `.ercue` 包结构（以**当前** Cue 端 `ercue_io.py` 为准，**不照抄旧文档**）【已核实】
```
xxx.ercue  (zip, ZIP_DEFLATED, compresslevel=6)
├── cuesheet.json        # 必需；主数据
├── media/               # 可选：内嵌素材（导出时勾"一起打包"才有）
└── thumbs/              # 可选：缩略图（Cue 端目前未写）
```
`cuesheet.json` 顶层字段（当前真实形态）：
`format_version`(=1) · `generator{tool,version}` · `created_at` · `min_app_version` ·
`requires_features[]` · `author{name}` · `title` · `notes` · **`res_w`/`res_h`（★新增可选，缺省 1920×1080）** ·
`media[]` · `tracks[]`。

- **media[]**：`{clip_id, name(basename), sha256, embedded(bool), duration_sec, has_alpha}`。
- **tracks[]**：`{track_key, identity{...}, composition{layers[]}}`。
  - `identity`：`fp_id`(指纹签名 `fp2-<hex>`) · `file_md5`(★认歌最高优先) · `meta_id` · `title` · `artist` · `duration_sec` · `bpm` · `key` · `file_name`。
  - `layers[]`：`{lyr_id, name, z, blend, opacity, items[]}`。
  - `items[]`（**拍为主坐标**）：`{item_id, clip_id, at_beats, at_sec(冗余), end_beats, src_in_sec, src_out_sec, speed, crop([x,y,w,h] 归一化|None), xform{scale,x,y,rot}, trans_in, trans_in_beats, trans_out, trans_out_beats, snap(遗留), note, blend(★新增,""=继承本层), opacity(★新增,null=继承本层)}`。

> **单位纪律**：文件里 `at_beats/end_beats/trans_*_beats` 是**拍**（主坐标），`src_in_sec/src_out_sec/speed` 是**秒/倍率**。演出端读文件后：**时间类一律用拍**（与位置源/指纹同一坐标系），**素材内起止用秒**。**不要**把 `at_beats` 转成秒再用（那会引入 `bpm` 二次换算误差，重复 Cue 端已做过的换算）。

### 2.2 包内含 `media/` / `thumbs/` 时
- 导入时若 zip 顶层有 `media/`：解压到 **`<包路径>.media/`**（如 `show.ercue.media/`），**幂等**（目标目录已存在且非空 ⇒ 直接复用，不重复解压）——与 Cue 端 `_extract_embedded_media` 完全同一约定【已核实 Cue 端实现，演出端照抄语义】。
- `media/` 内的文件名 = `MediaRef.name`（basename）；运行时 `clip_id → 路径` 映射：内嵌 → `<包路径>.media/<name>`；非内嵌 → 用户指定的素材目录（按 `name` 递归匹配）。
- `thumbs/`：**忽略**（缩略图只是编排端 UI 用；演出端不消费）。

### 2.3 歌曲识别 / 对齐（★最核心）
流程：**指纹认歌 → 取该曲目 identity → 用 `bpm` 得 beat_len → 指纹给出"歌内第几秒" → 换成"第几拍" → 喂 `CueRuntime.update(pos_beats)`**。
1. **认歌（五级降级，与 Cue 端 `match_track` 完全一致）**：`md5 → fingerprint → meta → title+artist → file`。Cue 端 `CueSheet.match_track()` 已有该实现【已核实】，演出端可**直接复用同一套判定逻辑**（把 `cuesheet.py` 原样放回时即自带）。★ 关键：`file_md5` 是**确定判据**（同一文件），优先于指纹。
2. **拍长**：`beat_len = 60 / bpm`（bpm 取该 `TrackEntry.identity.bpm`；bpm 缺失/无效 ⇒ 退化 `1 拍 = 1 秒`，**绝不猜 BPM**）。⚠ **必须与 Cue 端 `units.py` 的退化规则逐字一致**，否则两端对"拍↔秒"的理解不同 ⇒ 整条码表错位。
3. **位置**：`fp.py` 的 `FingerprintDB.match()` 每 ~0.5s 给一次"当前放到第几秒"，两次之间**用挂钟外推**（单调）。票数门槛 `CUE_FP_POS_MIN_VOTES=40`、最大年龄 `CUE_FP_POS_MAX_AGE=3.0s`（备份常量，沿用）。
4. **防抖**：回滞 0.15 拍、大跳变（>8 拍）直接重算不做过渡（见 §4 运行时）。

### 2.4 两端对齐契约（6 条，**不可单边改**）【已核实 Cue 端实现】
1. **几何**：`xform` 全默认 ⇒ **cover（`max(W/iw,H/ih)` 铺满裁切）**；有任一变换（scale/x/y/rot） ⇒ **contain（`min*us` 完整显示）**。crop 后以**裁切尺寸**为新基准。
2. **fade 曲线 = α²**：`op = opacity × alpha`；`trans=="fade"` 时再 `× trans_p`（`alpha` 已含淡入量 ⇒ 有效 α²）。slide/zoom/glitch/cut 不额外乘。
3. **能力表**：`trans_glitch` / `trans_zoom` 两端都支持（`requires_features` 里出现也要能渲染，**不当"将被忽略"**）。
4. **内嵌素材**：包内有 `media/` ⇒ 解到 `<包路径>.media/`，**幂等**。
5. **`src_out_sec`：到达出点冻结最后一帧**。★ 备份旧实现**未消费**该字段；为与 Cue 端预览一致，**演出端必须补上**。
   **落地方式 = 持帧，不 seek**：运行时把 `play_sec` 钳到 `src_out`（`src_ended=True`），渲染端**继续用上一帧 `_cue_last_frame`**（不黑、不越过）。**不**为"冻结"而发起 seek —— 持帧零成本、且比寻址可靠（HEVC/长 GOP seek 可能 800ms+，见 §4.3b/§4.6）。
6. **位置来源 = 指纹认歌**（本版不做设备源）。

## ③ 交互方式

### 3.1 怎么导入 `.ercue`
- **入口（推荐最小改动）**：`ui_main` 的「⋯ 更多」菜单加一项 **「码表（演出端）…」**（旧实现是 `act_cuesheet` "码表 / 时间码…"，见 `_bak_ui_main_before_strip.py:2093`）。点开 = 一个**轻量对话框**（不是第 3 页签）：
  - 「导入 .ercue…」（文件对话框，多选可选）· 最近文件 ·
  - 「绑定到图层」下拉（选一个已存在的**码表图层**）· 「启用」勾选 · 「卸下」按钮 ·
  - 一行**状态**（当前码表名 / 认出哪首 / 命中级别 / 当前拍位 / 位置来源）。
- **拖放**：可选（把 `.ercue` 拖进主窗 ⇒ 等同"导入"）。**优先级低**，一期可只做菜单。
- **命令行**：可选（`--cue <path>` 便于排障/自动演出）。**一期可不做**。

### 3.2 导入后挂到哪里（图层 or 独立码表层）
- **挂到一个「码表图层」（容器图层）** —— 沿用旧设计的"图层徽标/容器层"模型（`panels` 的 `btnCue`、`ui_main` 的 `cue_sheets` 注册表、引擎的 `is_cuesheet`）。理由：这样码表能和其它图层一样**排序/显隐/solo/不透明度**，且天然融入现有图层体系（用户 2026-09-28 要求"在演出台的图层这里选要用哪一个码表"）。
- **码表图层的特殊**：它是"容器"，自身无单一 player，画面由内部**子层**按码表渲染（`_draw_cuesheet_layer`）。**必须在小眼睛/可见性、solo、不透明度上表现与普通图层一致**【已核实旧实现踩过"码表图层盖在最上不受 solo 管"的坑】。
- **一期建议**：允许"一个码表图层绑定一张码表"（`lay.cuesheet_id`）。多码表并存 = 多个码表图层。**不做**"一个图层叠多张码表"（无需求、徒增复杂度）。

### 3.3 怎么启停 / 从哪一拍走
- **启停**：`启用` 勾选 = `lay.is_cuesheet=True` 且 "装载码表"；卸下 = `engine.clear_cue_sheet()`（回到普通图层）。小眼睛关掉 = 完全不检测（`cuesheet_wanted()` 返回 False，可据此**连指纹都不订阅**）。
- **从哪拍走**：**完全跟随播放位置**（指纹给出的歌内拍位）。**不提供"手动跳拍"** 于一期（DJ 现场用打碟机的 loop/jump 来移动，指纹会跟着走）。
- **不进接管三条件**（任一 ⇒ 该帧清空、退回普通图层，见 `_cuesheet_tick` 注释）：①没装载码表/认不出曲目；②没有可靠位置（票数不足/结果过期）；③图层不可见。

### 3.4 出错时的可见反馈（★用户要求，且要注意日志是否落盘）
- **【已核实】AutoVJ 没有全局 `logging.basicConfig` / `FileHandler`**（`grep` 只命中引擎自带的 `_LayerHealthLog`——那是**图层健康日志**（`engine.py:88`，写文件·滚动保留），不是通用日志）。⇒ **仅靠 `print/logging` 在 exe 里用户看不到**。
- **替代（用户可见）**：
  1. **导对话框内的一行状态**（码表名/认歌结果/命中级别/当前拍/来源）——最直接。
  2. **主窗状态栏**（旧实现用 `self.lbl_warn.setText(...)`，见 `_bak_ui_main_before_strip.py:4662`；**【待核实】**当前 `ui_main` 是否仍有 `lbl_warn` 或等价状态标签）。
  3. **装载/卸下/缺素材/版本不符** 用 `QMessageBox`（重要错误）+ 状态栏（常驻）。
  4. **`_LayerHealthLog` 里记码表子层的降级**（缺素材/取帧失败），滚动保留，便于事后排障。
- **绝不静默**：任何"码表本该接管却回退了"都要有一条**用户可见**原因（"没认到歌/位置丢失/缺 3 个素材"）。

### 3.5 与现有三页签 / 图层体系的关系
- **现有三页签**（演出台 / 素材·曲库·曲风 / …）**保持不变**；**不新增第 3 个"编排页"**（旧的第 3 页是编排，本次不做）。
- **码表图层徽标（btnCue）**：**做** —— 点图层头徽标 ⇒ 弹"这个图层用哪张码表"的菜单（旧实现 `_cue_layer_pick`，`_bak_ui_main_before_strip.py:4620+`）。这是"在演出台直接选码表"的最小交互，**不做**它的话用户得进对话框才能换表。**【待核实】**当前 `panels.py` 的图层头是否还留有徽标位置/容器层特殊处理（旧的已删，需要按 `_bak_panels_before_strip.py` 补回）。

### 4.3b `seek(sec)` 实现规范（**A′**，实测驱动）

> ★ **实测推翻了原担心**：15Hz 连打 10s（每 4 帧一次）磁盘均值最坏 **34.6MB/s**、峰值 36.5MB/s、CPU 最高 **4.66 核**（门槛 120/250，余量 **6.8×**；当年事故是 12 核 / 750MB/s）⇒ **"频繁 seek"不会复现 9-30 事故**。
> **真正的约束 = 单次 seek 延迟 ∝ GOP 长度**（实测）：DXV（GOP=1）**1.85ms**；长 H.264（GOP≈30）**75.8ms**；**短 H.264（整段仅 1 关键帧，GOP≈109）664ms**；长 HEVC（GOP≈143）**848ms**。

**A′ 六条硬约束（Step4 必须照此实现）**
1. **`seek` 在解码线程执行**：渲染线程（`_compose`）**只投递目标 `play_sec`（O(1) 引用赋值），绝不等待/阻塞**。← 安全底线。
2. **触发条件 = 片段进入 + 漂移 > 阈值**（`|player_pos - play_sec| > 0.35s`；**DXV 用 0.10s**）。**不做"每 4 帧校正"**（实测虽便宜，但无必要、且会放大抖动）。
3. **入场前预热 seek**：预加载窗口提前 **1~2s** 先 seek 到 `src_in`，把长 GOP 的 664~848ms **藏到入场之前**（配合 `warm_up`）。
4. **`src_out` 冻结 = 持 `_cue_last_frame`，不 seek**（契约⑤）。
5. **seek 失败/超时 ⇒ 降级"继续用当前帧"**，**绝不因此重开容器**（重开容器=磁盘风暴的形状）。每次 seek 失败记一次**限流**健康日志。
6. **格式分级**（按 `probe` 的 `codec`/GOP 或实测首帧延迟定档）：**DXV ⇒ 可用最严阈值（逐帧校正几乎免费）**；**H.264 ⇒ 入场 + 漂移校正**；**HEVC / 超长 GOP ⇒ `只入场 + 预热锚定`，容差放宽 ≈1s**（见 §4.6）。

**`seek(sec)` 的唯一正确语义**：`container.seek(backward=True)` **之后必须顺序 decode 到 `pts >= sec` 的目标帧**（= "seek + 前驱解码补齐"）。**只 `container.seek()` 不补齐 = 落点误差 P50 0.166~1.672s / max 2.4s**（见 §4.3c 坑①）—— 对卡点码表是**致命**的（画面停在上一段）。

### 4.3c 实现陷阱（**防 Step4 直接 `container.seek()` 当"跳到 sec"用**）

- **坑①：PyAV `container.seek()` 只落到"前一个关键帧"** —— 不补齐时落点误差 **P50 0.166~1.672s、max 2.4s**。⇒ `seek(sec)` **必须**实现成 **"seek + 前向解到 `pts >= sec`"**。直接调 `container.seek()` 当"跳到 sec"，就是"**seek 成功但位置错**"的根源。
- **坑②：不同后端语义不同**：`cv2.CAP_PROP_POS_MSEC` **精确**（误差 2~9ms）但**更慢**；PyAV `container.seek` **快但只到关键帧**。二选一，**实测**，别凭直觉混用。
- **坑③：`frame.reformat()` 每次新建 swscale 上下文更慢**（Cue 端已踩）⇒ 按目标尺寸**缓存 `VideoReformatter`**（复用 Cue 端思路）。
- **坑④：事故形状 = "取不到帧就重开容器"** —— 必须**禁止**；失败一律**退避 + 用上一帧**（退避 2s，同 Cue 端 `media.frames` 的 `RETRY_SEC`）。

### 4.4 性能红线（用户明确要求"性能与资源占用评估"）
- **渲染热路径（`_compose`）只做轻量提交**：读 `lay.cs_states`（`_cuesheet_tick` 已算好）+ `player.current()`（解码在各 player 线程）+ `_draw_layer`。**禁止**在 `_compose` 里开容器/解码/认歌/IO。
- **认歌与位置**：指纹结果本来就是"每 0.5s 一次"的异步快照，`_cue_pos_from_fingerprint` 只**读快照 + O(1) 外推**，不得在渲染线程做 FFT。
- **解码器激活/回收（历史事故防线）**：每帧 `_cue_set_active(lay, active_paths)` 必须**两个缓存都遍历**（`lay.cache` + `lay._cue_players`），把不在用的 `set_active(False)`。**漏掉 ⇒ 每碰过一个素材就多一个解码器一直解码**（实测 12 核 / 磁盘 750MB/s）。
- **预加载策略**：在 `_cuesheet_tick` 里，对"**下一个将要出现的 item**"（同层 `at_beats` 之后最近的）提前 `warm_up()`（预解首帧）；提前量 ~**1~2 秒**（按拍换算）。**上限**：预热的解码器数计入 `_cue_players` 上限。
- **每帧开销预算**：目标 **相对当前 fps 退化 < 1%**。测量方法：用现有 fps A/B 基准（参考 `brand/ui_audit/_fps_ab.py` 同类脚本），对比"码表关闭 / 码表接管"两种状态的 `compose p50/p95/max` 与 `video_fps`。
- **内存**：同时激活的解码器 ≤ `POOL` 上限；`_cue_players` 按 LRU 逐出并 `close()`；切歌/卸表时 `clear_cue_sheet` 关闭全部 cue 解码器。

- **不做 `position_source.py`**：本版只用指纹（§1.3 / §2.4 契约 6）。

### 4.6 GOP / 编码相关的**已知限制**（是播放器解码特性，**不是码表 bug**）

- **现象**：**HEVC / 超长 GOP 素材**（整段仅 1 个关键帧，GOP 109~143 帧 ≈3.6~4.8s）上，码表切换可能**晚 ≤1s** 才对齐（先显示旧/上一帧，下一拍才追上）。**不影响** DXV / 短 GOP H.264（DXV 1.85ms、长 H.264 ~76ms，肉眼无感）。
- **原因**：seek 只能落到关键帧，必须**前向解到目标帧**；长 GOP 这一段的成本 664~848ms（实测）**无法"零成本消除"**，只能靠**入场预热**（§4.3b 约束③）把它藏到片段开始前。
- **量化口径（写进说明书 / 状态栏提示）**：
  | 素材类型 | 对齐延迟（实测） | 观感 |
  |---|---|---|
  | DXV（GOP=1） | **1.85ms** | 无感 |
  | 长 GOP H.264 | **~76ms** | 无感 |
  | 短 GOP H.264（整段 1 关键帧） | **~664ms** | 可能慢一拍 |
  | 长 HEVC | **~848ms（≤1s）** | 可能慢一拍（已知限制） |
- **给用户的建议**：卡点要求极高的曲子，**优先用 DXV 或短 GOP 的 H.264 导出素材**；HEVC 素材请预留 **~1s 容差**，不要在"必须精确卡点"的段落用超长 GOP。
- **不要做的事**：**不要**为了"追帧"而每帧 seek / 重开容器 —— 那会从"慢一拍"恶化成"磁盘风暴"（§4.3c 坑④）。

# 附录 A · 两端数值对照脚本验收口径（`tools/twoside_parity_check.py`）

> 定位：**测试先行**。这些断言验的是"**算法/换算**"，不是"跑起来没崩"——专抓"错了也照样跑、但结果全错"的问题（risk3 与变速方向）。
> 约束：**纯逻辑、零 GUI、可 CI**（只 import 两端零 Qt 模块）。产出 `PARITY_OK` 或逐项 diff 表。

## A.0 输入
- `--pkg <path.ercue>`：一个真实码表包（从 `%LOCALAPPDATA%\EasyRealityCue\` 取，或 Cue 端导一个；脚本内也可内置一份 `SPEC_SAMPLE` 兜底，用于无包时自检）。
- `--bpm <float>` 可覆盖；缺省取 `tracks[].identity.bpm`。
- 容差：**`TOL = 1e-6`**。

## A.1 ★口径更正（必须先对齐，否则整条码表错位）
Cue 端 `at_beats` 是**相对曲首 t=0 的拍数**，`ercue_io` 的换算是
**`at_sec = at_beats * (60 / bpm)`，不减任何 anchor**（`units.beats_to_sec`；退化 `bpm≤0 ⇒ 1 拍=1 秒`）【已核实：样例 `32 拍 @155.03bpm → 12.3847s`，文件中 `at_sec=12.384` 只是冗余截断值，Cue 端**信任 at_beats、忽略 at_sec**】。

> 因此对照脚本用 **`anchor_beats = 0`**。
> **若演出端为指纹定位引入 beatgrid 相位 `anchor`（首拍在曲内的偏移），它属于"位置源"范畴，绝不能反向改写文件格式换算**（否则两端对同一包算出不同的 `at_sec`）。相位只在 **A.2 的 (1b) 位置一致性** 里出现，且必须由"位置源 → pos_beats"这一段独立断言，不混入 (1a) 的文件换算。

## A.2 对照项（逐值比对，`TOL=1e-6`）

| # | 项 | 断言式（对包内**每个 item**） |
|---|----|------------------------------|
| **1a** | 文件换算 | `at_sec == at_beats * (60/bpm)`；`end_sec == end_beats * (60/bpm)`（`end_beats=None ⇒ end_sec=None`）；`trans_in_sec == trans_in_beats*(60/bpm)` 同 `trans_out` |
| **1b** | 位置换算（**仅验位置源**，与文件无关） | `pos_beats == (t_track_sec - anchor) / (60/bpm)`；本版 `anchor=0`（指纹给的秒 ÷ beat_len）。**退化**：`bpm≤0 ⇒ pos_beats == t_track_sec`（1 拍=1 秒） |
| **2** | 时长恒等式（Cue 端 `reconcile_item_timing`） | `abs((end - at) - (src_out - src_in)/speed) <= TOL`。**仅当 `src_out` 非 None**；`src_out is None` 时：若 `src_dur` 已知则比 `(src_dur - src_in)/speed`，否则该行置 `N/A`（不算失败） |
| **3** | 变速方向（**验 ×speed 不是 ÷speed**） | 取 `src_in=0, src_out=10, speed∈{0.5,1,2}` ⇒ `timeline_len = (src_out-src_in)/speed` 期望 **20 / 10 / 5**。若得到 **5 / 10 / 20** ⇒ **FAIL（用了除法=慢放）** |
| **4** | `src_out` 冻结（算法断言） | 令 `frame_t(t) = min(src_in + (t-at)*speed, src_out)`；对 `t > at+(src_out-src_in)/speed` 采样 3 点，断言 `frame_t(t) == src_out`（**帧时间戳恒定理**）。注：`src_out=None` ⇒ 不冻结，此步行 `N/A` |
| **5** | fade 曲线 α²（给 3 采样点） | `opacity=1`、`trans_in=fade`、`L=trans_in_sec`：`t∈{at, at+L/2, at+L}` ⇒ 有效 α 期望 **`0 / 0.25 / 1.0`**（`a_in=t/L`，`trans_p=a_in`，有效 `=opacity*a_in*trans_p=a_in²`）。容差 `1e-6` |
| **6** | 几何 cover/contain（2 样例，`us=1`） | **G1** 源 1920×1080 → 画布 1440×1080：`cover= max(1440/1920,1080/1080)=1.0`、`contain= min(...)=0.75`。**G2** 源 1440×1080 → 画布 1920×1080：`cover= max(1920/1440,1080/1080)=1.333333`、`contain=1.0`。判据：xform 全默认 ⇒ 用 cover；有任一变换 ⇒ 用 contain |

> 补充（建议同时验的**结构一致性**）：对同一 `.ercue`，`Cue 端 ercue_io.load()` 与 `AutoVJ 端 cuesheet.py` 读出的 `at_beats/end_beats/src_in/src_out/speed/crop/xform/trans_*/res_w/res_h` 以及**片段有效 blend/opacity**（`item.blend or layer.blend`、`item.opacity if not None else layer.opacity`）逐值相等（`TOL`）。这一步直接证明"两个 exe 读同一包得到同一组数值"。

## A.3 运行方式 / 产出
- `python tools/twoside_parity_check.py --pkg <path> [--bpm 128]`；把两端 `src` 插入 `sys.path`（Cue 端零 Qt 模块：`ercue.model.units` / `ercue.model.ercue_io`；AutoVJ 端：`cuesheet` / `cuesheet_runtime`）。
- **Step1 之前**可先跑"**参照自检**"：只用 Cue 端 loader 对上述 1a/2/3/4/5/6 断言（验证参照实现本身）；**Step1 之后**再加"AutoVJ loader vs Cue loader"交叉比对。
- 退出码：全过 `0` + 打印 `PARITY_OK`；任一失败非 `0` + 打印**逐项 diff 表**（`项 | 期望 | 实得 | 差 | PASS/FAIL`）。
- **CI 化**：放进 `tools/` 的回归入口，随每次改动跑；**不过 = 不许进 Step4（热路径）**。

# 附录 B · 性能与资源验收口径（可直接执行的门槛）

> 起因：9-30 移除码表的导火索是 **"12 核跑满 + 磁盘 750MB/s"**。故验收**以"解码器生命周期 + 磁盘"为核心**，fps 只是表象。

## B.1 基线怎么取（固定场景，3 次取中位）

## B.2 数字门槛（全部满足才算 PASS）

| 维度 | 指标 | 门槛 | 工具/方法 |
|------|------|------|----------|
| **fps** | `video_fps`（码表 ON） | **≥ 0.99 × baseline**（退化 <1%） | fps A/B |
| | `compose p95` | **≤ 1.01 × baseline p95**（含噪声） | 同上 |
| **CPU** | 进程 `cpu_percent(interval=1)` 增量（相对空闲基线） | 均值 **≤ +10**（%·单核）、峰值 **≤ +25** | `psutil.Process(...).cpu_percent` |
| | 系统 `psutil.cpu_percent` 增量 | **≤ +3 个百分点** | `psutil.cpu_percent` |
| **内存** | 进程 RSS 增量（≤4 个**活跃**解码器） | **≤ +150MB @1080p** / **≤ +350MB @4K** | `psutil.Process().memory_info().rss` |
| | 预热 2 分钟后的 RSS 斜率 | **< +2MB/min**（无泄漏） | 每 1s 采样→线性拟合 |

| **磁盘(重点)** | `io_counters().read_bytes` 均值（稳态 60s，无切镜） | **≤ 120 MB/s** | `psutil.Process().io_counters()` |
| | 10s 窗口峰值 | **≤ 250 MB/s** | 同上 |
| | 30 分钟回归斜率 | **≈ 0（无上升趋势）** | 每分钟读一次→拟合 |
| | **红线** | **≤8 活跃解码器且无内容变化时，持续 >200MB/s 超过 10s ⇒ FAIL**（疑似每帧重开 / 未 `set_active(False)`） | 同上 |

## B.3 ★解码器生命周期规范（这条不达标，上面所有数字都是假的）
| 时机 | 动作 |
|------|------|
| **创建**（按需） | 片段将出现前（预加载提前量 ~1~2s，按拍换算）**warm_up** 建解码器；或首次 `player.current()` 懒建 |
| **激活** | "当前片段"+"过渡中的片段"+"预加载的下一个" ⇒ `set_active(True)`（不激活则 `current()` 恒 None ⇒ 黑屏，历史坑） |
| **失活** | **每帧** `_cue_set_active(lay, active_paths)`：遍历 **`lay.cache` + `lay._cue_players` 两个缓存**，不在 `active_paths` 的 **`set_active(False)`**（**这是 12 核事故的根因防线**） |
| **回收** | `_cue_players` 超 `cache_max` ⇒ **先失活再 `close()`**（LRU 逐出；绝不只从 dict 删引用而不关容器） |
| **切歌** | `_cuesheet_autoswitch` 换曲 ⇒ 重建 runtime，旧 `_cue_players` 全关 |
| **卸下/清空** | `clear_cue_sheet(silent=True)` ⇒ 全部 `close()`、清 `cs_states/_cue_items/_cue_last_frame` |
| **退出** | `engine.close()` **之前** `clear_cue_sheet(silent=True)`，确保无残留线程/句柄 |
| **连续快速启停** | 启停**幂等**；`_cue_set_active` 每帧兜底；反复 30 次后**活跃/缓存计数回到基线** |

> **口径修正（对我正文 §4.4 的细化）**：正文写的 `max(32, len+16)` 是**缓存条目上限**（可含失活项），**不是活跃解码器上限**。真正防事故的是 **"活跃 ≤ 8 + 每帧失活"**：4K 一个解码器 ~77MB，若 32 个全"活跃"就是 2.4GB 且 12 核满载。**验收看活跃数，不看缓存数。**

## B.4 验收方式 / 时长 / 判定
- **工具**：`psutil`（CPU/RSS/handles/io）+ 现有 `stallwatch.py`（卡顿看门狗）+ fps A/B harness；新增 `tools/cue_resource_probe.py`（每 1s 采样→CSV）。
- **时长**：fps A/B **3×30s**；CPU/内存 **稳态 60s**；**泄漏/磁盘 soak 30min**；另有 **连续快速启停 30 次**压力小测。
- **判定**：§B.2 **全部绿** + §B.3 生命周期无缺口 + soak 无上升趋势 ⇒ PASS；任一红线（尤其磁盘那行）⇒ FAIL，回到 Step4 修。
- **交付物**：`baseline.json` / `cue_on.csv` / 一份 `PERF_REPORT.md`（逐项 期望 vs 实测）。

# 附录 C · `_draw_layer` 补 `crop` 形参（热路径最小改动）

> 目标：让码表子层能裁切，**且对"没有 crop"的既有行为**做到**逐像素零变化**。

## C.1 改法（最小侵入、向后兼容）
1. 签名末尾**追加关键字参数**：`def _draw_layer(self, p, lay, img, W, H, prog, tr, pulse, snap, drift_x=0.0, drift_y=0.0, crop=None)` —— 现有所有调用点（普通图层/glitch/subtract）**不传 crop**，默认 `None`，**不受影响**。
2. 在内部把 `crop` 先归一成**源矩形** `src_rect`（复用 Cue 端 `_crop_src_rect` 的取整/钳位规则：`cw/ ch` 取整、`cx/cy` 钳到 `[0, iw-1]/[0, ih-1]`、越界收缩到 `-cx/-cy`）。`crop` 非法/None ⇒ `src_rect = None`。
3. **适配基准**：`iw, ih = (src_rect.width(), src_rect.height()) if src_rect else (image.width(), image.height())` —— **crop 时以裁切尺寸为 cover/contain 基准**（对齐 Cue 端 `_target_src`）。
4. **绘制分支（关键：零变化保证）**：
   - `paint_cover` 内：
     - `if src_rect is None:  painter.drawImage(_tgt, image)`  ← **完全保留原调用**（不传源矩形）；
     - `else:                painter.drawImage(_tgt, image, src_rect)`（源矩形重载，**不先 copy**）。
   - 旋转分支同理：`src_rect is None` 走原 `drawImage(_tgt, image)`，否则 `drawImage(_tgt, image, src_rect)`。
   - **glitch 分支**已经是"源矩形重载"，把它的 `src` 由"按行切整幅"改成"在 `src_rect` 内按比例切"即可（无 crop 时 `src_rect=None` 用全幅，行为不变）。
5. **不新增每帧分配**：`src_rect` 每帧算一次 `QRectF`（几字节），可忽略；**绝不** `image.copy()`。

## C.2 为什么这样就"零变化"
- `crop=None` ⇒ `src_rect=None` ⇒ **走的是与今天一字不差的 `drawImage(tgt, image)` 调用**；`iw/ih` 仍取全幅 ⇒ `k`、`tw/th`、目标矩形**全部同值**。故无 crop 场景**逐像素 bit-identical**。

## C.3 QA 验收（必须做，防止误伤普通图层）
- **无 crop 场景逐帧像素 diff**：固定一个含**普通图层 + 过渡(slide/zoom/glitch)** 的场景，改造前后各渲同一时间点的 30 帧，**要求 0 个差异像素**（`QImage` 逐 byte 比对）。
- **crop 场景**：给一个 item 设 `crop=[0.1,0.1,0.8,0.8]`，与 Cue 端同参数渲染同帧，diff 在容差内（证明两端裁切一致、且不拉伸）。
- **性能**：无 crop 场景 fps/compose 与 baseline 逐值一致（见附录 B）。
