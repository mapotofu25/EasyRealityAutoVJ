# ERAVJ 指纹识别精准度验证报告

- **日期**：2026-10-27
- **验证人**：QA（严过关）
- **验证对象**：`src/fp.py` 的 `FingerprintDB.match()` + `audio_engine.py` 的 `fp_lock_gate()`（纯函数）
- **指纹库**：`%LOCALAPPDATA%\AutoVJ\fingerprints.db`（主库 308MB + WAL 407MB，只读临时副本）
- **测试脚本**（tools/ 下 `_` 前缀，已 gitignore）：
  - `_qa_fp_accuracy.py`（本地逐段测试）
  - `_qa_fp_e2e.py`（本地端到端流式测试）
  - `_qa_fp_bili.py` / `_qa_fp_bili_stream.py`（B 站重编码测试）

---

## 1. 结论（TL;DR）

**有条件放行，未完全达标。**

| 参考线 | 实测 | 判定 |
|---|---|---|
| 误识别 ≤ 2% | 真·误锁定 1.0%（逐段）/ 端到端硬误 0% | ✅ **达标** |
| 本地 ≥ 95% 正确 | 端到端正确锁定 90.2%；逐段 top1 正确 90.4% | ⚠️ **未达**（差 ~5 个百分点） |
| B 站重编码 ≥ 80% 正确 | top1 正确 80.6%（勉强达线），但端到端仅 1/3 锁对 | ⚠️ **临界 / 未达** |

**核心判断**：
1. **防误识别做得很好**——把"锁错一首完全不同的歌"压到了 0%（端到端）/ 1%（逐段）。`fp_lock_gate` + 电池引擎的双重把关有效。
2. **短板不是"认错"，而是"认不出 / 认到同曲的不同版本"**：
   - 门栏 `fp_lock_gate` 偏保守，逐段测试误拦了 30.7% 的**正确**匹配（多为前奏/安静段落票数不足）。
   - B 站重编码音频的 top1 常是正确的，但单点票低（6~57 票），被门栏几乎全拦 ⇒ 现场锁不上。
   - 同 EP / 同曲多版本（Power Generator 4 版、Dust flac/mp3）会互相误锁——这是音频指纹的固有限制，占端到端"锁错"的全部。

## 2. 测试对象与方法

### 2.1 链路
```
音频文件 → soundfile 按原生采样率读 4.5s 片段 → fp.FingerprintDB.match(sig, sr)
        → 复算 fp_lock_gate(sid, votes, tot, second_best, second_tot, hit_rate)
        → 分类：正确 / 软误(同名不同版本) / 硬误(别歌) / 漏识别
```

- 窗口 **4.5s**（与 `audio_engine.FP_WIN_SEC` 一致）。
- 指纹库只读**一次性复制**到 `%TEMP%` 的副本（db + `-wal` + `-shm` 三件套），不碰正在运行的库。
- 白名单复现 `ui_main._allowed_song_ids()`：`music_meta[*].song_id` + `md5(music_library 路径)[:8]` + `cue.fp_songs[*].song_id` + `imported_lib.songs`（本项目 imported_lib 为空）。

### 2.2 三个口径
1. **逐段（snapshot）**：每首取 3 个固定位置（30%/55%/80%）各 4.5s 跑一次 match，看单窗表现。
2. **端到端（e2e）**：把每首歌按 0.5s hop 连续流式喂进 `match()` + `fp_lock_gate`（未锁定才把关）+ 真实 `ChargeBarEngine.tick()` 累计，看**最终能不能锁定正确的歌**。这才是"实时歌曲识别"真实正确率。
3. **B 站重编码**：对已下载的 B 站 PV/BGA 抽音频，同上流式验证鲁棒性。

### 2.3 分类定义（系统层，gate 放行才算锁定）
- **正确**：top1 ∈ 目标录音组（同 `fp_id`，byte-identical 录音）且 gate 放行。
- **软误**：top1 是**同名不同版本**（跨编码/跨专辑，song_id 仍错）且 gate 放行。
- **硬误**：top1 是**完全不同的歌**且 gate 放行（会锁错 cue）。
- **漏识别**：`sid=-1` 或被 gate 拦下（含 top1 正确但票不足）。

## 4. 结果

### 4.1 本地曲库 · 逐段（198 片段）

| 指标 | 数量 | 占比 |
|---|---|---|
| match top1 = 目标录音（同 fp_id） | 179 | **90.4%** |
| match top1 = 同名不同版本（软误） | 6 | 3.0% |
| match top1 = 别歌（硬误） | 13 | 6.6% |
| match top1 = 无结果（sid=-1） | 0 | 0% |
| —— 正确 top1 被 gate 放行 | 124 | 62.6%（占正确 69.3%） |
| —— 正确 top1 被 gate 误拦 | 55 | 27.8%（占正确 30.7%） |
| —— 错误 top1 被 gate 拦下 | 12 | 6.1% |
| **真·误锁定（错误 top1 且过 gate）** | **2** | **1.0%** |
| **系统正确锁定（单窗）** | **124** | **62.6%** |
| **漏识别（单窗）** | **72** | **36.4%** |

要点：
- 13 例"别歌"top1 里，**6 例是 Power Generator 同 EP 不同 mix**（Main Mix↔Radio Cut↔Instrumental，本质同一首歌），真正"完全不同歌"只有 7 例（Extra Pain→揽月、Floating Globe→Dragonborn、G.A.B.→Can't Handle、Outburst Oxygen remaster→原版、System Overloaded→Save The World），且**票数全部 3~15，被 gate 全部拦下**。
- 唯一一例 gate 放行的硬误：**Power Generator (Main Mix) → Radio Cut**（单点 156 票 ≥80 直通），仍是"同 EP 不同版本"。

### 4.2 本地曲库 · 端到端（41 首 × 90s 流式 + 电池引擎累计）

| 指标 | 数量 | 占比 |
|---|---|---|
| **正确锁定** | 37 | **90.2%** |
| 软误锁定（同曲不同版本） | 4 | 9.8% |
| **硬误锁定（完全不同歌）** | **0** | **0.0%** |
| 未锁定 | 0 | 0.0% |

- 首次正确锁定耗时：**中位 8.5s**（min 2.0s / max 27.5s）。
- 4 例软误锁定全部是"同一首歌的另一个版本"：Power Generator（Main Mix→Radio Cut、Radio Cut→Main Mix、Instrumental→Main Mix）3 例 + Dust（flac↔mp3）1 例。

> 端到端 vs 逐段的差别：逐段测的是"任意 4.5s 窗一次命中"，门栏保守导致单窗 36% 漏识别；但现场是**连续采样 + 电池引擎跨窗累计**，所以端到端正确锁定率显著更高（90.2%），且**硬误锁定为 0**。

### 4.3 B 站重编码（3 首，流式逐窗）

| 样本 | top1 正确率 | gate 放行窗 | 端到端锁定 |
|---|---|---|---|
| Nimbus Spark 1999（48k→48k） | 96.4%（264/274） | 24 | ✅ 锁对（25.5s） |
| 西行谣（44.1k PV） | 96.7%（231/239） | 4 | ❌ 锁错（1.5s 锁到 1!2!3!☆） |
| 揽月（44.1k 母带 → 48k 剪辑版） | 51.8%（147/284） | 0 | ❌ 未锁 |
| **综合 top1 正确率** | **80.6%（642/797）** | — | 1 锁对 / 1 锁错 / 1 未锁 |

要点：
- **采样率一致的母带（Nimbus 48k→48k）鲁棒性良好**，top1 96.4% 且能锁对。
- **揽月是"母带 44.1k + B 站 48k + 新春宴剪辑版(447s→151s)"三重差异叠加**，top1 正确率掉到 51.8%，且正确 top1 的单点票仅 6~9（命中率却 89~97%）⇒ 过不了 gate 的"单点 ≥80 / 变速兜底 ≥15"，全程锁不上。
- **西行谣 top1 96.7% 但端到端锁错**：PV 开头 intro 先被另一首 Sociable State 曲（1!2!3!☆）以高票抢先锁定，随后正确匹配票数偏低，撑不起 ChargeBarEngine 的"换歌证据"（4s 内累计 ≥60 票、峰值 ≥15），锁不回来。

## 6. 结论与放行建议

### 6.1 达标判定
| 参考线 | 实测 | 判定 |
|---|---|---|
| 误识别 ≤ 2% | 逐段真·误锁定 1.0%；端到端硬误 0% | ✅ 达标 |
| 本地 ≥ 95% 正确 | 端到端正确锁定 90.2%；逐段 top1 90.4% | ⚠️ 未达（差 ~5pp） |
| B 站重编码 ≥ 80% 正确 | top1 80.6%（临界）；端到端仅 1/3 锁对 | ⚠️ 临界/未达 |

### 6.2 三个必须报告的问题（只报告，不修）
1. **`fp_lock_gate` 门栏偏保守 → 漏识别为主**：逐段测试把 30.7% 的**正确**匹配误拦（票数不足）。现场靠电池引擎跨窗累计才补回来，但代价是首次锁定中位 8.5s、个别曲目 27.5s。对"实时"体验偏慢。
2. **B 站/重编码音源锁不上**：B 站音频（重编码 + 常为剪辑版 + 采样率变化）正确 top1 的单点票只有 6~57，够不到 gate 的"单点 ≥80"或"变速兜底 ≥15"。变速兜底（`fp_lock_gate` 的第二条路径）本为 DJ 调速设计，但对"重编码导致的票数摊薄"仍不够宽。
3. **同曲多版本互相误锁**：Power Generator 4 版、Dust flac/mp3 共享大量相同音频，短窗无法区分版本 ⇒ 端到端 9.8% 的"锁错"（全部是同曲不同版本，非实现 bug，是指纹算法固有限制）。

### 6.3 放行建议
**不建议无条件放行「实时歌曲识别 + BPM/八拍对齐」的后续工作**，建议按以下前提分档：

- ✅ **可放行的场景**：现场只放**本地曲库原文件**（无重编码/剪辑/变速）。此场景端到端正确锁定 90.2%、硬误锁定 0%，是安全的；仅需接受"同 EP/同曲多版本会锁到同名版本"这一已知限制。
- ⚠️ **需先改进再覆盖的场景**：B 站/重编码/剪辑音源。当前这类音源 top1 虽 ~80% 正确，但门栏几乎全拦、端到端锁定 1/3。改进方向（供工程师参考，非本次职责）：(a) 放宽变速兜底的"单点 ≥15"阈值或引入"命中率高 + 总票领先"的更宽判据；(b) 同曲多版本用全曲签名 `fp_id` 做版本消歧或合并白名单。
