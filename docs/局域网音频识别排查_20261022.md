# 局域网音频「无法识别指纹」排查报告（2026-10-22 22:10）

## 结论（先给判定）

**ERAVJ 侧的问题，不是 ERSND。**

更准确地说：**音频链路完全正常**（收包、解码、能量、BPM、指纹哈希命中率全部正常），
卡在**曲库白名单**——正在放的那首歌不在本机曲库列表里，所以匹配器按设计返回 0 票。

---

## 一、完整链路与各环节证据

```
A 机 ERSND 发送端
   └─ UDP 47811（float32 交错，48k）
        └─ B 机 lan_audio_recv.LanDevice（收包 + 抖动缓冲 60ms）
             └─ _LanRecorder.record()（按块取数，缓冲过深丢帧）
                  └─ audio_engine._capture_loop（能量/BPM/指纹环形缓冲）
                       └─ fp.fingerprint_audio → FingerprintDB.match（白名单过滤）
                            └─ ChargeBarEngine（确认识别）→ 码表
```

`cue_health.log` 实测（22:10:15 ~ 22:10:37，局域网音源）：

```
db=1 eng=1 run=1 buf=576000(12.0s) silent=0.0s lvl=0.75~0.87
engy=0.74~0.97 bpm=140.5~142.5
hit=208/217~219/238  seg=0.312 sig=216000/0.312 raw=0 cur=-1 allow=118
```

逐项判读：

| 字段 | 数值 | 说明 |
|---|---|---|
| `buf=576000(12.0s)` | 满 | 音频**持续在进**，接收端没断流 |
| `lvl=0.75~0.87` | 正常大声 | 不是静音、不是极低电平 |
| `bpm=142.5` 稳定 | 正常 | 节拍分析能跑 → 波形连续、无明显断点 |
| `sig=216000/0.312` | 4.5s @48k | 送进识别器的采样率/长度都对（48k） |
| **`hit=208/217`** | **96% 命中** | **查询哈希几乎全部能在库里找到** → 音频内容与库内录音一致，传输没有变调/丢声道/重采样错误 |
| **`raw=0`** | **0 票** | 匹配器一个对齐候选都没返回 |
| `allow=118` | 白名单 118 | 只允许曲库/导入库/码表里的 118 个 song_id 参与匹配 |

代码里对这两个字段的判据（`audio_engine.py:1600-1603` 注释原文）：

> `n_hash` 正常且 `hit≈0` ⇒ 音频不是库里那首（声道/重采样/源不对）
> **`hit` 很多但 `votes` 恒 0 ⇒ 匹配器/选取逻辑有问题**

本次是后者。

## 二、定位到具体是哪一首

库里存在**白名单外的完整指纹**（不是噪声）：

```
song_id 2295330989 → 41545 行指纹（正常一首歌 2~4 万行）
其余 5 个白名单外 id 只有 1~5 行（杂散）
```

用库内文件逐一比对，`2295330989` 对应：

```
<素材库>\2of\tofu\Rolling Contact - Can We Believe That.flac
匹配票数 227，offset=30.0（取样点 30s）⇒ 证据确凿
```

但当前 `config.json`：

```
music_library 66 条 —— 不含 Can We Believe（0 条）
music_meta    65 条 —— 同样不含
文件本身存在：True
```

**即：这首歌的指纹还在库里（旧 id），但歌已经不在曲库列表里了。**
白名单只允许"当前曲库 + 导入库 + 码表曲目"，于是它的 4 万行指纹**全部被过滤** →
哈希命中率 96%，但一票都不计 → 表现为"局域网音频认不出"。

## 三、为什么可以排除 ERSND

| 若 ERSND 有问题，应出现的现象 | 本次实测 |
|---|---|
| `lvl` 长期 0 / 断流 | 0.75~0.87，持续有值 |
| `hit≈0`（变调、丢声道、采样率错） | **208/217 = 96%** |
| BPM 乱跳 / 无 BPM | 140.5→142.5，稳定 |
| `buf` 不增长 | 12s 满缓冲 |
| 丢包率飙升 | 无断流告警 |

另外，接收端"缓冲过深丢帧"（`lan_audio_recv.record()`，目标 60ms、超过 96ms 丢）
理论上会制造断点，但实测（`tools/_lan_jitter_probe.py`）即使制造 350ms 堆积、
`trimmed=11`，指纹仍能匹配（票数 100）——**说明丢帧不足以造成 0 票**。

---

## 四、修复建议

1. **把该曲加回曲库**（曲库页「添加文件/文件夹」→ 重新扫描），
   让 `music_meta` 写入它的当前 `song_id`；下次识别即可命中。
2. 若希望"指纹在库里就能认、不必加曲库"，需要放宽白名单——
   但会重新引入**误识别**（那 5 个杂散 id 与过期歌曲正是之前修掉的假阳性来源），
   不建议。
3. 已加**指纹 id 自愈**（`ui_main._heal_fp_ids_bg`）：曲库里**仍有**的歌曲，如果
   指纹存的是旧路径 id，启动时用实测票数（≥100、offset≈取样点）自动改挂到当前 id。
   ⚠ 本曲因为**已不在曲库**，自愈不会动它——这是符合预期的。
