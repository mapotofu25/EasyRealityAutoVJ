# 本地音乐分析 + 素材匹配 · 方案设计

> 目标：在本机（离线、无网络）把一首歌"像人耳一样"听成结构，再把结构映射到素材，
> 并给每段素材产出标签 / 关键词 / 动态范围 / 亮度等属性。
> 本文只做方案论证，不含代码改动。

---

## 一、总体架构（四层，离线算、线上只读缓存）

```
音频文件 ──①解码──► 单声道 22.05k
                   │
                   ├─②节拍层：BPM / 拍点 / 小节头 / 变速曲线
                   ├─③能量层：响度(RMS·LUFS) / 低频占比 / 谱通量 / 亮度(质心)
                   └─④结构层：自相似矩阵 → 段落边界 → 段落类型
                            │
                            ▼
                      music_structure.json（每首歌一份，缓存）
                            │
素材库 ──⑤素材特征──► clip_features.json（亮度/对比/运动/动态范围/标签）
                            │
                            ▼
                     ⑥匹配器（规则打分 + 约束）──► 码表片段建议 / 直接导出 .ercue
```

**核心决策：分析全部离线、一次性、可增量。** 演出时只读 JSON，不跑任何模型 —— 这是保证现场不卡的前提（与现在 `music_meta` 里缓存 BPM/节拍网格是同一思路）。

## 二、工具/模型选型（本地可跑）

### ① 节拍与速度

| 工具 | 作用 | 说明 |
|---|---|---|
| **Beat This!**（项目已用，`src/phrase_bt.py`） | 拍点 + 小节头（downbeat） | 已在跑，别重复造；对电子乐很稳 |
| **madmom**（RNN/DBN） | 拍点、downbeat、节拍强度 | 老牌、准；注意 numpy 版本兼容 |
| **BeatNet**（CRNN+粒子滤波） | 实时节拍跟踪 | 若要"边播边跟"才需要；离线可用前者 |
| **librosa** | 变速曲线（`beat_track` + 局部窗口）、onset 强度 | 纯 CPU、轻量，适合做二次校验 |

建议：**Beat This! 为主，librosa 做一致性校验**（两者 BPM 差 >2% 时取置信度高者）。

### ② 能量 / 音色 / 亮度

| 指标 | 工具 | 对应用途 |
|---|---|---|
| 短时 RMS、峰值 | numpy + librosa | 能量包络（段落强弱） |
| **LUFS（EBU R128）** | `pyloudnorm` | 与"人耳响度"一致，比 RMS 更贴近听感 |
| 低频(20–120Hz)/中/高频占比 | librosa STFT | 判 drop（低频猛增）、breakdown（低频消失） |
| 谱通量（spectral flux） | librosa | 变化点检测、build 的"越来越密" |
| **亮度**（spectral centroid / rolloff） | librosa | 素材"亮/暗"要和音乐高频能量匹配 |
| 音色向量（MFCC 统计） | librosa | 聚类段落音色 |

### ③ 曲式结构（段落）

三条路线，建议组合：

1. **自相似矩阵 + 谱聚类**（librosa `recurrence_matrix` → `agglomerative`）
   经典 MIR 做法，能找出"重复的副歌"和"新段落"，纯 CPU、无需模型。
2. **Novelty 曲线（Foote）**：对 SSM 做核校验，峰值即边界；适合"时机切换"。
3. **神经嵌入聚类**（更强，可选）：
   - **MERT-v1-95M** / **MusicFM**：自监督音乐表征，逐帧嵌入 → 聚类边界，对电子乐段落更敏感。
   - 需要 PyTorch，95M 模型 CPU 也能跑（慢 3~5 倍）。

**段落类型判定**（不靠模型，靠可解释规则，便于调参）：

| 类型 | 判据（示例，可调） |
|---|---|
| Intro | 前 10%，能量低、低频占比低、无鼓（onset 稀疏） |
| Build | 谱通量持续上升 + 高频占比上升 + 能量爬坡，≥8 小节 |
| Drop | 低频占比骤增（+15%↑）、LUFS 跳升、拍点密度最大 |
| Breakdown | 低频骤降、能量下降 >6 LUFS、人声/铺底为主 |
| Outro | 后 10%，能量递减、元素减少 |

> 你现有代码里已有 `phrase`（小节相位）与 `bpm/anchor`，段落只需在"小节网格"上判定，**不需要重新做节拍**。

### ④ 音乐语义标签（可选增强）

| 工具 | 产出 | 备注 |
|---|---|---|
| **PANNs（CNN14）** | AudioSet 527 类（Electronic/Drum and bass/...） | 轻量、CPU 可跑 |
| **Essentia EffNet-Discogs** | 400 种风格 + mood/danceability 模型 | 风格标签更细；ONNX 版可跑 |
| **LAION-CLAP** | 零样本：自定义中文/英文词表打分 | 想要"空灵/赛博/故障"这类词，CLAP 最合适 |
| Qwen2-Audio（可选） | 一句话描述段落 | 显存 ≥8G 才建议；仅做"人话描述"，不参与判定 |

### ⑤ 素材侧（视频/图片）属性

| 属性 | 算法 | 说明 |
|---|---|---|
| 亮度 | 平均 luma / HSV-V | 与音乐高频能量对齐 |
| 动态范围 | luma 的 p95−p5（或直方图熵） | 你要的"高动态/低动态" |
| 对比度 | 全局 std / 局部对比 | 强拍可配高对比 |
| 运动量 | 帧差均值、光流幅值 | drop 配高运动 |
| 闪烁度 | 帧间亮度方差 | 高频段配闪烁 |
| 主色/饱和度 | HSV 直方图 | 冷/暖调匹配 |
| Alpha 占比 | 解码后 alpha 均值 | 透明素材可叠层 |
| 循环性 | 首末帧相似度 | 决定能否 loop |
| 语义标签 | **CLIP 零样本**（同一套中文词表） | 与音乐标签共用词表才能匹配 |

> 项目里已有 `tagger.py`（自动打标）与 DXV 解码链，可直接扩展，不必新建管线。

## 三、匹配算法（可解释优先，学习排序兜底）

### 1) 统一向量空间

音乐段落向量 `M`：
`[能量, 低频占比, 谱通量, 亮度, 拍密度, 是否 drop/build/breakdown]`

素材向量 `C`：
`[亮度, 动态范围, 运动量, 对比度, 闪烁, 饱和度, 标签one-hot]`

### 2) 规则打分（第一版，够用且可调）

```
score = w1·亮度匹配 + w2·能量匹配 + w3·运动匹配 + w4·标签重合 − w5·重复惩罚
```

典型规则：
- **Drop** → 高运动 + 高对比 + 高饱和 + 低动态范围（避免糊）
- **Breakdown** → 低运动 + 低对比 + 高动态范围（留白）
- **Build** → 运动量随时间递增的素材（可用斜率筛选）
- **Intro/Outro** → 低运动 + 可循环

### 3) 硬约束（现场必须）

- 同一素材在 N 秒内不重复（N 可配，默认 90s）
- 素材时长 ≥ 段落时长（或允许 loop 的才放行）
- 切点对齐到**小节头/八拍**（你已有 `anchor + 8n×beat_len`）
- Kv/颜色等全局开关不参与匹配（保持"素材独立"）

### 4) 进阶：用你已有的码表做"偏好学习"

你机器上已有大量 `.ercue`（人工编排结果）——这是**现成的监督数据**：

- 正样本 = 人工把某素材放在某段落
- 负样本 = 同段落里没被选的素材
- 训练一个 **LambdaMART / 小型 GBDT**（LightGBM，纯 CPU）做排序
- 特征就用上面的 `M`、`C` 与交叉项

这比手调权重稳，而且**完全本地**、训练几秒完成。建议第二期做。

## 四、落地路径（三期，风险递增）

### 一期：结构分析（1~2 天可跑通）
- 复用 Beat This! 的拍/小节
- librosa 算 RMS/LUFS/低频占比/谱通量/亮度
- SSM + novelty 切段，规则判类型
- 产出 `music_structure.json`（段落表：起止小节、类型、能量、亮度）

**验收**：拿 5 首你熟悉的歌，段落边界与人工标注差 ≤ 2 小节。

### 二期：素材属性 + 规则匹配
- 抽帧算亮度/动态/运动/闪烁（每素材 0.2s 抽 8 帧即可）
- CLIP 零样本打标签（词表 ≤ 60 个，中文）
- 规则打分 + 约束，输出"每段建议 top-5 素材"

**验收**：人工看 20 段建议，接受率 ≥ 60%（第一期目标）。

### 三期：学习排序 + 端到端
- 用历史 `.ercue` 训练 LightGBM 排序
- 一键"分析整包 → 生成码表草稿 → 在编排端微调"

**验收**：与人工编排的素材重合率 ≥ 50%，且不出现"同素材连播"。

## 五、性能与资源（本机实测口径）

| 环节 | CPU 耗时（单曲 5 分钟） | 显存 |
|---|---|---|
| 解码 + 特征（librosa） | 3~6 s | 0 |
| Beat This! 推理 | 2~4 s（GPU）/ 8~12 s（CPU） | <1 G |
| SSM + 聚类 | 1~2 s | 0 |
| PANNs / EffNet 标签 | 2~4 s | <1 G |
| CLAP（可选） | 3~5 s（GPU） | ~2 G |
| 素材抽帧 + CLIP（每 100 个素材） | 20~40 s | ~2 G |

**结论**：纯 CPU 也能全流程跑，单曲 < 15 s；GPU 可压到 5 s 内。可后台批量、断点续算。

## 六、关键风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 段落边界抖动 | 电子乐段落靠"元素进出"，能量曲线可能平台化 | 用"低频占比 + 谱通量"双通道判据，别只看 RMS |
| BPM 变速曲 | 半速/双速歧义 | 用 Beat This! 的小节头做校验，`[115,185]` 门控保留 |
| 素材属性太粗 | 只抽 8 帧会漏运动 | 运动量单独按 0.1s 抽 16 帧算 |
| 标签词表漂移 | 音乐与素材词表不一致 → 匹配失效 | **共用一份词表**（配置文件），两边都只从这份取 |
| 现场卡顿 | 误把模型放进渲染线程 | 分析全部离线；线上只读 JSON（铁律：主线程不做耗时活） |
| 授权/许可 | Essentia 模型多为 CC-BY-NC | 商用需确认；PANNs(CC-BY)、CLAP(Apache-2.0) 更宽松 |

## 八、一句话结论

**能做，且不需要大模型也能做得很稳**：

- 节奏/能量 → `librosa + pyloudnorm`（纯 CPU，秒级）
- 曲式 → `自相似矩阵 + novelty`，边界再按"低频占比/谱通量"分类
- 语义标签 → `PANNs` 或 `Essentia EffNet`；想要自定义中文词就用 `CLAP`
- 素材属性 → 抽帧统计 + `CLIP` 零样本（与音乐共用词表）
- 匹配 → 先规则，后用你已有的 `.ercue` 训一个 LightGBM 排序

最关键的工程原则：**分析离线、缓存成 JSON、线上零模型**。
