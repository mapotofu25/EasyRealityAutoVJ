## 关键证据（`cue_health.log` 原文）

**① BPM 估计「双倍」后撞 220 上限，直接把正确匹配否决**

```
16:43:41 [R] ... lvl=0.0000 engy=0.575 bpm=219.5 hit=211/224 ... gate=none
        lbpm=128.0 rbpm=219.5 brel=0.715 bpmok=0
        pick=702506326 pv=24 ptot=119 p2=98 phr=0.97
```

- `pick` 就是正确的 Raccoon Memes，`phr=0.97`（97% 哈希命中）——识别本身没错；
- 但 `rbpm=219.5`：真实 128 BPM 的**双倍 256 被 `min(220)` 钳到 219.5**，
  `brel=|128−219.5|/128=0.715` 远超 `BPM_MATCH_TOL=0.20`，且 219.5/128=1.72 不在倍频集 `(0.5,1,2)` 里
  ⇒ **BPM 校验否决了一个 97% 命中的正确匹配**。
- 同一个数值不稳定：单独探针里同一首歌读的是 `127.5`（`brel=0.004 bpmok=1`，正常锁定）。

`Extra Pain`（100 BPM）同样被双倍，只是 100×2=200 **没撞顶**，靠倍频放行救了回来：

```
16:49:24 [R] ... bpm=210.5 ... lbpm=100.0 rbpm=210.5 brel=1.106 bpmok=1
```

## 结论

Round5 的差不是「这批歌都认不出」，而是两条**与被测曲目无关的判据问题**：

1. **`min(220)` 上限 + 无「双倍修正」** ⇒ BPM 落在 ~110~183 区间、又被估成双倍的歌，
   会得到一个「既不等于真值、也不是整数倍」的 219.5，然后被 BPM 校验误杀。
   这直接影响现场主力曲速段（House/Trance/中速 Hardcore 都在 110~183）。
2. **`2× 领先` 判据遇同专辑近似曲目失效**：正确曲的总票可能还不如同专辑另一首，条件天然不成立。

**在 ① 修掉之前，继续 roll 更多歌只会重复同一个失败模式**（D/E 两组 0/6 已经全被 ① 覆盖）。
