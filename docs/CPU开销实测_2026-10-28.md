# CPU 开销实测与优化 · 2026-10-28

> 起因：用户反馈「5800X 上要 30% CPU」。先用 `psutil` 按线程拆，再用受控 A/B 逐项关掉功能对比。
> 本机：16 逻辑核；输出 1280×720 / 8 图层 / 渲染 30fps；曲库 65 首。

## 一、实测数字（放歌中，单核百分比 = 一个核的占用）

| 环节 | 成本 | 怎么测的 |
|---|---|---|
| 全部（受控：固定素材、不自动切）= | **~70% 一个核**（≈4% 整机） | `_perf_ab.py`，3 次中位，样本 70/70/59 |
| 音频分析 `_Analyzer.feed` | **~1%** | `_perf_feed.py`（20s 音频跑 0.16s） |
| 指纹识别 `fp.match` | **~14%** | `_perf_fp.py`：单次 35~47ms，循环 0.3s 一拍 |
| 渲染 30fps → 20fps | **−19 点**（70% → 51%） | `_perf_ab.py` 同条件换 `perf.render_fps` |
| NDI 开 vs 关 | **无可测差异**（60.9% vs 60.9%） | 受控 A/B，各 3 次 |

## 二、两个必须说清的结论

**① 先前「NDI 吃 0.75 个核」是误判。**
未控制变量时测到 `NDI 开 164% / 关 90%`；但那时**自动切素材**在跑，解码负载随机。
把 `mode.auto=False` + `auto.energy_gate=False` 固定素材后重测：**开和关中位值完全一样**。
⇒ NDI 在本机不是主要开销。**NDI 限帧那条代码已按用户要求整段删除**（不留配置项），
   NDI 路径与以前逐行一致。

**② 主要开销在「渲染 + 切素材解码」，不在识别链。**
识别链合计约 15%（分析 1% + 指纹 14%）；剩下 ~45 点都在渲染/合成/取帧。
渲染帧率是最直接的杠杆：30fps → 20fps 省 19 点（整机约 1.2%）。

## 三、本版实际改动

| # | 改动 | 性质 |
|---|---|---|
| 1 | 删掉**每块都算一次**的「未钳位 BPM」340 桶直方图（消费者已随上一版判据回退被移除） | 纯删死活，无行为变化 |
| 2 | （已删除）NDI 限帧开关 —— 实测无收益，用户要求不要，代码已全部移除 | — |
| 3 | `_perf_cpu.py` / `_perf_fp.py` / `_perf_feed.py` / `_perf_ab.py` / `_perf_ndi.py` | 测量工具（gitignored 风格） |

## 四、给 5800X 的调优建议（按收益排序）

1. **渲染帧率**：`perf.render_fps` 30 → 20（实测 −19 点/核）。VJ 画面 20fps 通常够用。
2. **确认 `perf.gpu_decode = True`**：本机因为 GL 驱动问题只能用 `False` 测，
   `False` 下取帧是 CPU 软解——同分辨率下这是最贵的一项。你的机器开着就是对的。
3. **NDI**：720p 实测与关闭无差异，不用管；4K 若发现吃不消，再单独议（当前无开关）。
4. **图层数**：8 图层每帧都要合成一遍，减到实际用到的数量，线性省。
5. 指纹识别固定吃 ~14% 单核（每次匹配 35~47ms / 0.3s 一拍）。要再降只能改判据节奏，
   会影响切歌反应速度，本轮没动。

## 五、复现

```bash
venv\Scripts\python.exe -u tools\_perf_cpu.py 40          # 总量 + 按线程拆
venv\Scripts\python.exe -u tools\_perf_fp.py              # 指纹单次耗时
venv\Scripts\python.exe -u tools\_perf_feed.py            # 分析循环实时占比
venv\Scripts\python.exe -u tools\_perf_ab.py 15 3         # 受控 A/B（固定素材，取中位）
```

> ⚠ `psutil.cpu_percent(interval=None)` 的窗口太短会读出 0.0 —— 一律用阻塞 `interval=1.0` 采样。
> ⚠ 测 CPU **必须固定素材**（关自动切换与能量门控），否则测到的是"这把碰巧换了什么素材"。
