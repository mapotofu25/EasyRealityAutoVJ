--------------------------------------------------------------------------------
  src/native/dxvlz.c     DXV3 帧里那层 LZ 中间压缩的解压（解出来就是 BC 压缩块）
                         —— 依据 FFmpeg dxv.c 的公开算法重写，独立编译成 DLL、动态链接，
                            不链接也不修改 FFmpeg 本体

  tools/build_dxvlz.py   编译脚本（只在开发机需要 zig，一次几秒）
  tools/_extract_zig.py  zig 包按需抽取（避免解压 19565 个文件）
  tools/dxv_gpu_verify.py / dxv_gpu_bench.py   正确性与性能验证

二、正确性：逐像素比对通过
--------------------------------------------------------------------------------
真实素材 30 帧，与 FFmpeg 软解逐像素比（0~255 尺度）：

  0 (6).mov       DXT1 1080p    R 0.22  G 0.35  B 0.20   A 0.00   最大 6   → 一致
  1 (1) (2).mov   DXT1 4K       R 0.29  G 0.39  B 0.18   A 0.00   最大 6   → 一致
  1 (9).mov       DXT1 4K       R 0.19  G 0.42  B 0.36   A 0.00   最大 6   → 一致

  平均色差 < 0.5、最大 6/255 —— 肉眼无法分辨。顺带也证明了方向（上下不翻转）是对的。

三、性能：**收益取决于「格式 + 尺寸」**（60 帧 × 3 轮，CPU 累加测量，ms/帧）
--------------------------------------------------------------------------------
  素材            项目                        CPU      墙钟
  DXT1-1080p     GPU 路径合计                 2.86     2.86
                 FFmpeg 软解 4 线程            2.34     1.68     ← GPU 反而略亏

  DXT5-1080p     GPU 路径合计                 3.91     3.90
                 FFmpeg 软解 4 线程            9.27     3.81     ← **省 58%**

  DXT1-4K        GPU 路径合计                 9.64     7.99
                 FFmpeg 软解 4 线程           13.54     7.40     ← 省 29%

  DXT5-超宽5280   GPU 路径合计                 8.07     5.41
                 FFmpeg 软解 4 线程           30.21    10.68     ← **省 73%**

  （GPU 路径 = C 的 LZ 解包 + GPU 解压/缩放/回读）

**结论：带 alpha 的 DXT5 和大尺寸素材收益巨大（58%~73%）；1080p 的 DXT1 不要走 GPU**
—— BC1 对 FFmpeg 本来就便宜，而回读（glReadPixels）要花钱。
所以集成时**按「格式 + 尺寸」决定**，不能一刀切。

四、顺带落地：解码线程上限（免费收益）
--------------------------------------------------------------------------------
FFmpeg 的 DXV 解码走"切片多线程"，而切片线程的开销在大画面上比收益还大：

  4K DXT5：16 线程 38.67ms CPU/帧  →  4 线程 12.89ms（**省 67%**）
  1080p DXT5：16 线程 12.05ms      →  4 线程 9.80ms

而每个解码线程有 33ms 预算（30fps），根本不需要"2.7ms 的低延迟"。
已加 `media_manager._cap_decode_threads()`（默认 `min(4, CPU核数)`，
环境变量 `AUTO_VJ_DEC_THREADS` 可覆盖，填 0 恢复旧行为）。真实素材验证播放正常。

七、本轮踩坑（都已写进项目记忆）
--------------------------------------------------------------------------------
  · Windows 的 `time.process_time()` 只在时钟中断（15.625ms）时更新 →
    单帧测量会得到 0.00/15.62 这种假读数（我第一版因此把 GPU 报成 15.62ms/帧）。
    **必须多轮 × 多帧累加再除。**
  · zig 0.16 没有 `--cache-dir` 参数，要用环境变量 ZIG_GLOBAL_CACHE_DIR / ZIG_LOCAL_CACHE_DIR
  · 沙箱里编译 zig 会 AccessDenied → 必须提权
  · pip 安装 ziglang 会解出 19565 个文件 / 363MB，在 P: 上要十几分钟
    （盘不慢，166MB/s；慢在"每个文件都过一次杀软"）→ 只抽需要的子集（6670 个，约 7 分钟）

八、集成完成（2026-09-25）
================================================================================
上面第七节列的四步，本轮全部做完：

1) 播放器：`src/media_manager.py` 新增 `GpuDxvPlayer`
     · 解码线程里 demux 取原始包 → dxvnative 解 LZ → glctx 把 BC 块直传 GPU 解压+缩放
       → 回读成 BGRA 的 QImage（换通道在**着色器里**做，不用 numpy 花式索引 ——
       那一步 1080p 要 1~2ms，正好把收益吃掉）
     · **全自动降级**：不是 DXV3 / 帧头不支持（DXV2-LZF、YCG6）/ 分辨率不是 4 的倍数 /
       GL 上下文建不起来 → 同一条线程里切回 PyAV 软解（与 AvAlphaPlayer 同构）。
       任何失败都不影响播放，绝不黑屏。
     · `.gpu` / `.reason` 两个属性可以直接看出某个素材走了哪条路、为什么。
     · 诊断还会打印原因；`gpu_status()` 给设置界面用。

2) 启用策略（按格式 + 尺寸，不能一刀切）
     DXT5 一律启用；DXT1 只在 ≥ 3.0 Mpx（约 1440p 以上）启用 —— 因为 DXT1-1080p
     实测**反而多花 46%**（BC1 对 FFmpeg 本来就便宜，而回读要花钱）。
     门槛可用环境变量 `AUTO_VJ_GPU_DXT1_MIN_PX` 调（调试用）。
     素材覆盖：DXV 共 144 个（DXT5 64 / DXT1 66 / 解析不了的 14）。

3) 界面：设置 → 效果 → 「GPU 解码（实验）」，**默认关**。
     勾上立即生效（对新开的播放器；已在播的等下一次切换才换路径，不打断演出）；
     机器不支持时弹一条提示并自动回退。只作用于普通图层，**Kv 待机层不受影响**。

4) 打包：glfw 已装进 venv，`build_exe.py` 加 `--collect-all glfw` +
     `--add-binary src/_dxvlz.dll`；`dxvnative.dll_path()` 同时认 `sys._MEIPASS`

九、集成后实测（和上面第二节"纯解码"的数字不是一回事 —— 这里是**播放器整条链**，
    含 开容器 + demux + LZ 解包 + GPU 解压缩放 + 回读 + QImage 拷贝）

测法：交替多轮取中位数，单位 = 核当量（1.0 = 占满一个核）。
⚠ 每次都要**先让播放器跑 1.5 秒**再开始计时 —— 不预热会把「开容器 + 建 GL 上下文 +
  编译着色器」算进去，同一条 DXT1 素材因此量出过"多花 46%"和"省 15%"两个矛盾结论。

[单素材 1080p]
  场景                                  开 GPU    不开(现状)    效果
  DXT5（不带 alpha，现状走 cv2）         0.224     0.443       省 49%
  DXT5（真带 alpha，现状走 PyAV）        0.214     1.042       省 79%
  DXT1（门槛挡住，仅供参照）            0.48      0.59        省约 15%（收益小、测量易飘）

[4 个图层同时播 DXT5-1080p（模拟演出），每组 18 秒]
  开 GPU   ：0.87 核   四层各 533 帧（≈29.6fps，满帧），工作集 374 → 377 MB
  不开     ：2.42 核   四层各 533 帧，工作集 882 → 855 MB
  → **省 1.55 个核（-64%）**

  ★ 这才是这个功能的意义：4 图层场景把解码占用从「2.4 个核」压到「0.9 个核」，
    4 核机器才有富余留给 VDJ / 直播 / 录制。

十、顺手修掉的两个既有问题（2026-09-25 当天发现、当天修完）
================================================================================
1) **105/164 个 .mov 因为 GBK 元数据根本探测不出来** —— `av.open(path)` 不带
   `metadata_errors="replace"` 时会抛 UnicodeDecodeError，于是：
     · `_av_probe_alpha` 探测失败 → 一律返回「无 alpha」→ 真带 alpha 的素材
       **透明通道一直是丢的**（走 cv2，第四个通道直接没了）；
     · `AvAlphaPlayer._open` 同样打不开（虽然轮不到它）。
   修复：4 处 `av.open`（`_av_probe_alpha` / `AvAlphaPlayer._open` /
   `AvAlphaPlayer._iter_frames` 重开容器 / `_make_av_thumb`）全部带上
   `metadata_errors="replace"`。

2) **旧判定只看 `pix_fmt`，把整批素材判错** —— DXV 的解码器一律输出 `rgba`，
   DXT1 素材的 alpha 通道全是 255，于是**25 个整段不透明的素材被误判成「带 alpha」**，
   白白走更贵的 PyAV + ARGB32 路径（实测比 cv2 贵 45%~55%）。
   修复：pix_fmt 说有 alpha 时，**再顺序解码最多 24 帧、每 4 帧检查一次**，确认 alpha
   真的不是全 255 才算「带 alpha」（只查第一帧不够 —— 透明可能只出现在中段）。
   `tools/_alpha_audit.py` 与 `tools/_alpha_perf_check.py` 都能复核这个判断。

   [全库校正结果：`tools/alpha_migration_selftest.py`，34 秒跑完]
     真带 alpha：14 个（其中 9 个是以前被漏判的，透明从此生效）
     纠正误判：25 个（改回 cv2，各约省 0.4 核）
     缩略图：PNG 30 → 14 个（**PNG ⇔ 真带 alpha**，判定链自洽）
     幂等：再跑一遍零变更
   ★ 净影响：25 个素材省 CPU、9 个素材花约 0.4 核/个换回真透明，整体仍是省的，
     而且画面对了。

3) 「是不是 DXV」以前没有缓存，只能开容器问（几十毫秒，不能放渲染线程）。
   加了后台编码普查（`CodecProbeWorker`，启动后 3 秒起跑，164 个约 2~4 秒），
   结果填进 `MediaItem._codec` / `_is_dxv`，之后切素材是零成本判断。
