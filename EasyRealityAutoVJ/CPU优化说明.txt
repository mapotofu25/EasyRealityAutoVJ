Easy Reality AutoVJ —— CPU 占用优化说明
更新于 2026-09-24，对应版本 2026.09.24.11
================================================================================

一、目标
--------------------------------------------------------------------------------
不是"提高帧率"，而是**把 CPU 解放出来** —— CPU 要同时跑 VirtualDJ、直播、录制。
所以看的指标只有一个：**这个软件占几个 CPU 核**（任务管理器里的百分比 = 核数 ÷ 核数）。


二、测量方法（以及一个必须知道的坑）
--------------------------------------------------------------------------------
测量工具：tools/cpu_profile.py
  · 起**真实的 MainWindow**，开始 VJ，播放真实音乐，跑 4 个图层
  · 用 Windows 的 GetProcessTimes 读**进程级** CPU（必须除以采样秒数才是"占几个核"）
  · 用 tools/thread_attrib.py 枚举**进程内全部线程**（含 C 库开的线程）

⚠ 坑一：**只看 Python 的 threading.enumerate() 会严重漏项**。
  引擎的 60fps 渲染线程（engine.moveToThread）、FFmpeg 的解码线程、OpenBLAS 的数学线程、
  Qt 的线程池 —— 这些**都不在 Python 的线程列表里**。
  以前"进程 4.8 核、Python 线程相加只有 0.7 核"这个黑箱就是它们。

⚠ 坑二：**本机单次采样噪声高达 ±1 个核**（这台机器有 30 多个虚拟显示器，属于远程/开发环境）。
  所以 0.5 核级别的结论**必须交替重复 3 轮以上取中位数**，单次读数不可信。
  （本次就因此先误报过一次"省 1.6 核"，见第四节。）


三、改了什么（全部零风险，不改画面、不改算法）
--------------------------------------------------------------------------------
1) 音频识别改环形缓冲          audio_engine._AudioRing
   原来每 0.5 秒要把整段音频缓冲**完整复制一遍**（几十万个 Python 对象搬运）。
   改为 numpy 环形缓冲后，这一条线程的占用从 0.78 个核降到 0.05 个核。

2) 限制 OpenCV 的内部线程       media_manager.py
   OpenCV 默认按 CPU 核数开线程池（本机 16 条），解码和缩放时抢核。
   改为 2 条。可用环境变量 AUTO_VJ_CV_THREADS 覆盖（0 = 恢复默认）。

3) 限制数学库（OpenBLAS）线程    src/main.py 最顶部
   numpy 用的是 scipy-openblas，而 OPENBLAS_NUM_THREADS **从来没有设过**，
   于是它默认按核数开线程池。而这套程序里的矩阵运算全是小规模
   （能量分频段、指纹匹配、曲风特征 88×512 / 96×128 之类），多线程的调度开销远大于收益。
   干净自检（同一个 700×700 矩阵乘）：限制前 OpenBLAS 开了 15 条线程、把核数吃满（**属极端状态，
不代表实际运行时的占用**）；限制到 1 条线程后占用大幅下降。
   现在设成 2，可用 AUTO_VJ_BLAS_THREADS 覆盖（0 = 关闭这个限制）。
   ⚠ 必须在 import numpy **之前**设置，所以放在程序入口最前面。

4) 限制推理引擎（ONNX Runtime）线程 + 关掉"自旋等待"
   audio_genre.py（曲风识别，演出时常驻）、tagger.py（素材打标，只在导入时用）
   onnxruntime 默认 intra-op 线程数 = CPU 核数，并且池线程在两次推理之间
   **自旋等待**（allow_spinning 默认开）—— 自旋是持续吃 CPU 的。
   现在：曲风 intra=2、打标 intra=4，双双关掉自旋。
   可用 AUTO_VJ_ORT_SPIN=1 恢复自旋、AUTO_VJ_ORT_THREADS=N 改线程数。

5) 没开 NDI 时不再拷贝音频     audio_engine.py
   原来不管 NDI 开没开，每块音频都要做一次无用的 asarray/reshape/copy。


四、实测效果（严格同条件、交替重复 3 轮取中位数）
--------------------------------------------------------------------------------
               旧行为（关掉以上全部限制）      本版
   第 1 轮            3.57 核                  3.10 核
   第 2 轮            3.18 核                  4.05 核
   第 3 轮            3.60 核                  2.98 核
   ------------------------------------------------------
   中位数            3.57 核                  3.10 核     → 省 0.47 核（−13%）

把 2) 3) 4) 5) 这四项合起来算，**在"限制全开 vs 全关"的同条件对照下**，中位数从 3.57 核
降到 3.10 核（−13%）。与更早的版本相比降幅更大，但当时的测量条件与现在不同，**不宜直接比较**。

⚠ 诚实说明：单轮波动可达 ±1 个核，所以"1.6 核"这类更大的数字是**噪声**，不要采信。
   上表的中位数才是可信结论。在**核数更少、负载更重的机器上**（比如 4 核老机器、
   或导入大量素材时），这些限制的效果会比这里更明显。


五、试过但**不值得做**的两件事（附数据）
--------------------------------------------------------------------------------
A) 让 AI 走显卡（DirectML）
   · 环境本身没问题：onnxruntime-directml 装得上、DmlExecutionProvider 能加载，
     D3D12 设备创建成功（RTX 3070 Ti）
   · 但 **CLIP 模型编译直接失败**：MLOperatorAuthorImpl.cpp 报 80070057（参数无效），
     把输入固定成 [1,3,224,224] 之后仍然失败 → 模型图内部的动态维度没有固定干净
   · ⚠ 而且这个报错是**宽字符写进 stderr、被 utf-8 解码搞坏**的，上层只看得到
     "codec can't decode byte" 这种垃圾信息；要用 utf-16-le 解原始字节才能看到真错
   · **更关键：就算修好也没有收益** —— CLIP 只在导入/给素材打标签时跑（一次性的），
     **不在演出路径上**；唯一常驻的曲风识别单次只要 1.99 毫秒（每 3 秒一次）
   → 结论：不做

B) 把预览/输出搬到显卡
   · 实测：界面 + 预览 + 输出窗口**全部加起来**只占 0.114 个核，是进程占用的 **3.8%**
   · 顺带纠正两个想当然的错误：
       以为"1080p 缩到预览尺寸"要 2.8 毫秒 —— 实际 QPixmap.scaled 只要 0.25 毫秒
       以为"两级缩放能提速" —— 实际反而更慢（0.76 毫秒 > 0.25 毫秒）
       真正贵的是 QPixmap.fromImage(1080p)，1.26 毫秒
   → 结论：不值得为一个 3.8% 的项重写整条渲染管线


六、顺带发现的两个问题（尚未解决）
--------------------------------------------------------------------------------
1) 引擎的 60fps 渲染线程占 **0.53 个核**（进程的 20% 左右）
   它由 engine.moveToThread() 创建，**不在 Python 的线程列表里**，所以以前所有的
   CPU 剖析都把它算进"其它"里，一直没被看见。60fps 下约 8.8 毫秒/帧
   （这是合成 + 颜色 + 后处理 + 输出派发的总和，属于必要开销）。

2) **9 条 Qt6Core 线程，合计约 1.3 个核 —— 而且停止 VJ 之后不释放**
   · 已排除：不是 QImage 缩放引起的（实测 QImage.scaled 完全不开线程池）
   · 已排除：不是预览/输出引起的（用空实现关掉它们，线程依旧存在）
   · 缩小到与 QThreadPool 相关（把池的线程上限改小，这部分 CPU 从 0.53 降到 0.15）
     但代码里**没有任何** QtConcurrent / QThreadPool 调用 —— 来源尚未查清
   · 停止 VJ 后仍保留 9 条线程，疑似线程泄漏
   → 这是下一步最值得查的地方（约占进程 40%）

3) 解码仍然是大头（约 1.5 个核，最大单块）
   素材是 DXV 编码，而 **NVDEC / QSV / D3D11VA 都不支持 DXV**，换不了硬件解码器。
   要真正解决只有三条路（都属于"重做渲染管线"级别的大工程）：
     A. 直接解析 DXV，把压缩块当显卡纹理上传（不转码，工程量大）
     B. 素材转码成 H.264 All-I，走显卡硬解
     C. 素材转码成 HAP（GPU 友好的 DXT 封装）
   本版**没有动解码**。


七、怎么自己复测
--------------------------------------------------------------------------------
采样与归因：
  venv\Scripts\python.exe tools\cpu_profile.py 18 10      （预热 18 秒，采样 10 秒）
  venv\Scripts\python.exe tools\thread_attrib.py 8        （列出全部线程）

想回退某一项限制（用于对比）：
  set AUTO_VJ_BLAS_THREADS=0        数学库线程不限制
  set AUTO_VJ_ORT_SPIN=1            恢复推理引擎的自旋等待
  set AUTO_VJ_ORT_THREADS=16        推理引擎线程数
  set AUTO_VJ_CV_THREADS=0          OpenCV 线程数恢复默认

其它相关工具：
  tools\decode_attrib.py      分层归因（哪一层引入多少 CPU）
  tools\decode_threads.py     解码线程数 vs 墙钟 / CPU
  tools\onnx_cost.py          两个 AI 模型的推理耗时基线
  tools\qt_threads_probe.py   Qt 线程归因
  tools\qt_scale_probe.py     Qt 缩放是否开线程池
  tools\dml_probe.py / dml_diag.py   DirectML 可行性


八、补充：Qt6 线程之谜已解开（对应第六节第 2 条）
--------------------------------------------------------------------------------
现象：开始 VJ 后出现 9 条 Qt6Core 线程（其中 1 条是引擎渲染线程），合计约 1.4 个核，
      停止 VJ 后不立即释放 —— 一度怀疑是线程泄漏。

实验（逐项累加关闭，每步 6 秒，**边泵 Qt 事件循环边采样**）：
   基线（全都开着）            Qt6  1.39 核（9 条）
   + 关预览 set_frame          Qt6  0.99 核（9 条）
   + 关输出 set_frame          Qt6  1.47 核（9 条）
   + 停状态栏定时器            Qt6  1.05 核（9 条）
   + 停引擎 60fps 定时器       Qt6  0.00 核（9 条）   ← 精确归零
   + 停音频采集                Qt6  0.00 核（9 条）
   停完后等 40 秒              Qt6  0.00 核（1 条）   ← 自动回收

结论：
  1) Qt6 那部分的 CPU **100% 来自引擎的每帧渲染** —— 停掉引擎定时器就精确归零，
     其它任何一项关掉都没有这个效果。
  2) 来源是 **Qt 6 的 QPainter 在合成图像时会自动并行化像素混合**（走 Qt 内部的
     线程池），所以引擎每合成一帧都会唤起这些 worker。我们的代码里**没有任何**
     QtConcurrent / QThreadPool 调用 —— 这正是当初查不出原因的地方。
  3) **不是泄漏**：停掉 40 秒后线程数从 9 自动回落到 1（线程池 worker 的正常过期行为）。
  4) 所以正确的优化手段是**降低渲染帧率**，而不是"修泄漏" ——
     已新增「渲染帧率」设置（60 / 30 / 20，见第九节）；素材大多 25 到 30fps，
     降到 30 能让这一整块（引擎合成 + Qt 并行混合）直接减半。


九、渲染帧率（本次新增的设置项）
--------------------------------------------------------------------------------
素材大多是 25 到 30fps，而引擎默认按 60fps 合成 —— 其中约一半是把同一帧重复合成一遍。

实测（**同进程内切换**，只盯"引擎渲染"这个量，避免解码的随机波动干扰）：

   60fps   引擎渲染 0.55 / 0.52 核
   30fps   引擎渲染 0.30 / 0.25 核
   → 渲染开销约减半（平均 0.53 → 0.27 核）

⚠ 为什么"进程总占用"看不出来：解码（与渲染帧率无关）本身的波动有 ±1 核，
   远大于这 0.26 核的信号 —— 所以必须用"同进程切换 + 只看渲染那一路"的方法才能测准。

同时排查这个功能时撞出并修掉了两个「主循环静默不启动」的隐患（详见当天日志）：
   · `engine_thread.started.connect(engine.start)` 的槽可能被按 QueuedConnection
     投递回**主线程**执行 → 跨线程 `timer.start()` **静默失败** →
     主循环完全不跑：黑屏、不切素材、不解码、CPU 近乎为零
   · 从主线程 `timer.setInterval()` 同样会把定时器停掉（Qt 先停表再按新间隔重启，
     而重启发生在错误的线程）
   两处都改成 `QMetaObject.invokeMethod(..., Qt.QueuedConnection)`（明确以接收者线程为准）。
