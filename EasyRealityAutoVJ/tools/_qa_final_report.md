## 1. ★ 220 例 harness 可信度判定

### 1.1 它到底怎么驱动
- 用**预生成「逐窗投票直方图」**（`tools/_fix3_hint_seq.json`，由 `tools/_fix3_d_hint.py` 采集真实 FLAC+真实指纹库）+ `FP.FingerprintDB._pick` 选点（= `fp.match` 的选点逻辑），**不是**在实时音频上真跑 `fp.match`，**不含** `charge_engine.tick` 确认。
- 录的是**每识别窗一个 offset**（`_grid_observe` 按 `recognized_t` 去重），与生产"每 0.5s 一窗"同粒度；`off_end = off + 4.5` 与生产 `recognized_offset = off + 4.5·r` 同轴。✅
- `tools/_gridfix5_handoff.py` 的 `recognized_offset` 虽每帧变，但 `recognized_t` 量化到 0.5s，`_grid_observe` 去重后**实际仍是每 0.5s 一窗** ⇒ 该"每帧"线索**不影响结论**。

### 1.2 ★ 窗间隔：harness = **1.0s**，生产 = **0.5s**（关键）
- `_fix3_d_hint.py`：`HOP=1.0, WIN=4.5`（为压体积只用 1.0s 取样）。
- 生产 `audio_engine._recognize_loop`：`sleep(0.5)` + ~30ms 匹配 ⇒ **≈0.53s/窗**。
- **dt 语义**：dt 以**挂钟秒**计、常量是秒 ⇒ "上锚 ≤4.0s"的**字面语义与窗率无关（成立）**。
- **但行为/结论强依赖窗率**：同一 4.0，在 1.0s 下 = 容忍 4 个窗，在 0.5s 下 = 容忍 8 个窗；锁定所需的"相邻可信对"密度也差一倍。**实测证实结论翻转（见 §2）。**

### 1.3 起点构造
- 起点 `[0,3,6,…,30]` 含义 = "首个可信窗出现在 t=N"，是"从第 N 秒起播"的**近似**（真实起播首窗会晚 ~0.5s，且需 4.5s 填窗）。可接受，但非严格等价。

**判定：harness 是"逻辑级代理"（真实素材/真实直方图/真实 per-song grid 128~155BPM），方向可信；但因其窗率=1.0s ≠ 生产 0.5s，其绝对数字与"平台/下限"结论不能直接搬到生产。**

## 2. 独立验证：我在生产节奏（0.5s）重采直方图复跑同一 220 例

自建 `tools/_qa_final_verify.py`（独立驱动现役 `_beat_pos`，不 import 工程师脚本），并用**真实 FLAC + 真实指纹库**按 0.5s/4.5s 重采直方图（`_qa_final_seq_half.json`）。

| dt | 1.0s harness（复现工程师） | **0.5s 生产（我独立测）** |
|----|--------------------------|--------------------------|
| | 总误锁s / 最长s / >5s / 覆盖 | 总误锁s / 最长s / >5s / 锁定中位 / 覆盖 |
| 1.0 | 0 / 0.0 / 0 / **0/220** | **0 / 0.0 / 0 / 44.2s / 220/220** |
| 1.5 | 0 / 0.0 / 0 / **0/220** | **0 / 0.0 / 0 / 41.0s / 220/220** |
| 2.0 | 208 / 32.0 / 8 / 220/220 | 156 / 38.5 / 8 / 23.5s / 220/220 |
| 3.0 | 48 / 32.0 / 3 / 220/220 | 96 / 24.0 / 7 / 23.5s / 220/220 |
| **4.0** | **48 / 32.0 / 3 / 220/220** | **97 / 38.5 / 6 / 23.5s / 220/220** |
| 6.0 | 171 / 54.0 / 5 / 220/220 | 421 / 53.5 / 17 / 22.0s / 220/220 |

CWB(t=0) / Lost(t=0)：1.0s：6.0→54.0/5.0、4.0→0.0/0.0；0.5s：6.0→**53.5**/0.0、4.0→**0.0**/0.0。**CWB 复现**。

**要点：**
1. **工程师的 6.0 基线逐值复现**（171/54.0/5/28.0/220）⇒ 口径自证成功。
2. **方向成立**：两种节奏下 6.0 ≫ 4.0（生产更明显：421→97 = 4.3×，harness 171→48 = 3.6×）。
3. **绝对量级 harness 低估 ~2×**（97 vs 48；421 vs 171）。
4. **"3~4 平台 / 不能低于 2.5"是 1.0s 假象**：生产 0.5s 下 1.0~1.5 反而 **0 误锁 + 满覆盖**（代价：锁定中位 41~44s vs 23.5s）。⇒ **4.0 在生产不是最优，偏松；但仍安全。**

### 2.1 残余"锁错"到底是什么错（重要，决定用户影响）
生产节奏 4.0 残余坏帧 5820 个，逐帧分析：
- **100% 是整拍偏移**（到最近整拍偏差中位 **0.007 拍**）⇒ **切点仍踩拍，不会出现"错拍"**。
- `err mod 8`：**60% = 0**（与正确相位相同 ⇒ 仅"锁到同段落的另一处"，**用户不可见**）；**40% = 4**（半乐句，切在另一条 4 拍线，**仍在拍上**）。
- 6.0 时：mod8=0 占 45%、mod8=4 占 55%。
⇒ **"误锁 |err|>1 拍"这一口径严重高估了可听危害**：最坏是"半乐句错位"，没有跑拍。

## 4. 新故障模式 / 边界

- **稀窗静默失效**：把窗拉到 2.0s → 20/20 锁；**3.0s → 仅 3/20**；**≥5.0s → 0/20（永不锁定，静默回退原 4 拍时钟）**。生产 0.5s 有充足余量，但若机器长卡（连续丢 7+ 窗）网格会静默不生效（**安全**，非误锁）。
- **`getattr` 回退 4.0 安全**：所有 dummy 未设 `GRID_CONSIST_MAX_DT` ⇒ 用 4.0，行为一致；全仓其余 `6.0`（energy/timeout 等）无对手语义被误伤。
- **换歌/中断/Loop 不误丢锚**：换歌 sid 变 ⇒ pending 重置；中断 sid<0 ⇒ 早退不碰时钟；已锁定后 Loop 不走 pending。`_gridfix5_handoff` S3 Loop 会有一帧 ~20 拍跳变（物理回跳，非本改动引入）。
- **上限 4.0 ⇒ 生产容忍 ≤4s 识别空档仍复用旧锚**；>4s 才丢弃。已锁定期的坏窗由 `jump_max=32拍` + 连续同向 + R3 兜底。
- **本轮改动隔离性**：`_grid_observe` 相对第六轮快照**仅 3 行语义变更**（`6.0`→`max_dt`，默认 4.0），无夹带。

## 5. 铁律 + 性能

- HUD 路径（`ui_main`→`engine.phrase_countdown/switch_countdown`）经 `GridClock` **自有 RLock**，**不碰** `engine._tick_lock`。✅
- `GridClock` 锁内**纯数学**（不 sleep/IO/事件）。✅
- `_publish_grid_hint` **不持 audio 锁**（仅写 float 属性，CPython 原子）。✅
- 无"图层性能豁免"、无"控件文本判分支"（panels 仅一处注释提及旧写法）。✅
- 性能（40 万次/项）：关网格 0.851µs；开+无识别 0.872µs；开+**已锁定** 2.283µs ⇒ **Δ+1.43µs/帧**（60fps 帧预算的 ~0.009%）。✅

## 6. 残留风险（含"测了没结论"）
1. **harness 非真实链路**：喂预生成直方图 + `_pick`，**未**含 `charge_engine` 确认、**未**真跑 `fp.match`、**未**走完整引擎 tick（图层/切换/HUD）。我的 0.5s 复采缩小了窗率差，但仍是逻辑级。
2. **无法做真实播放设备端到端**：需真实声卡/播放链路与真实时间轴，本轮**做不到**（未做，如实报告）。
3. **上限 4.0 非生产最优**：1.0~1.5 在生产把误锁降到 0（代价：锁定中位 41~44s）。是否换值属**调参决策**，非 bug。
4. **真实节奏 ≈0.53s 且带抖动**：我按理想 0.5s 采样；生产抖动会小幅影响 dt≤1.5 的余量（4.0 余量足够，故不影响"可交付"判断）。
5. **本地来源网格相位不可信**：仅 21 首有 VDJ 真值；其余靠本地估计，本改动不涉及。

## 7. 给用户的已知限制清单（可直接进说明文档）
> **节拍网格（八拍乐句对齐）当前状态与注意**
> - 本功能在**认出歌且扫描出该歌节拍网格**后才生效；**前 20~40 秒**通常在等识别稳定，此期间**自动按原 4 拍小节对齐**（正常现象，非故障）。
> - 极少数情况（歌曲**强重复段落**，如 `Can We Believe That`）可能**短暂锁到相邻乐句**：切点**仍在拍上**，但素材可能在"另一条 4 拍线"上换（最坏约 30~40 秒后自动纠正）。**不会出现错拍/跑拍。**
> - 若电脑**长时间卡顿**（连续数秒不出识别结果），本功能会**自动静默退回原 4 拍对齐**（安全，不会乱切）。
> - 未识别 / 无网格 / 关闭开关时，行为与旧版本**完全一致**。
> - 建议：**上线前在本机歌单上试听**；对强重复段落的歌，注意开场前 30 秒的换场表现。
