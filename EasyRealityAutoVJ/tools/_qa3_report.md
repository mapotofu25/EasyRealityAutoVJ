## 3. ★ 闭环自证偏差（本轮重点）—— **成立，且构成回归**

### 3.1 机制已被真实素材证实
`_qa3_real.py`（真实 FLAC + 真实指纹库）：Cosmic String 存在一处重复段（X1=102.0s 与 X2=217.2s 内容相同）。
- 查询窗取**真实** X2=217.2s：无 hint → off=217.20（正确，294 票）；**给 hint=102（错位置）→ off=101.98（被强拉到另一处，票 294→29）**。
- ⇒ **hint 能把匹配从真实位置主动拉到另一处**。闭环的「自证」通路成立。

### 3.2 可达性
20 首真实数据中，「同歌错候选、票≥120、距真值>HINT_W」出现 **74 段**，其中 **≥2 连续窗的有 7 段**（最长 11 窗，票~200）。只有 ≥2 连续强错窗才可能突破修法②。

### 3.3 制造出的回归（有明确 repro）
**根因链**（Raccoon Memes 起播于 t=5s，逐窗追踪）：
1. t=5~13：时钟未锁定（真候选票<120），自由跑，prov≈9。
2. **t=14：出现一个票=126 的错窗**（在歌里另一处，off=216.5），无 hint → 全局众数选它 → 写入 `_grid_pending`。
3. t≥15：未锁定分支**据 `_grid_pending` 发布临时 hint≈217** → 之后每窗 matcher 都在 hint±32 内选到那处错候选（真候选被挡在窗外）⇒ **自己把自己锁到错位置**。
4. 对比：**无 hint** 时 t=15+ 全局众数回到真位置，t=20 即自愈（off=19.0）。

| 场景（中途起播） | hint OFF | hint ON |
|---|---|---|
| Raccoon Memes 起 t=5s | 误锁 max **18 拍**，t=20 自愈 | 误锁 max **405 拍**，持续到 t≈50 |
| Demon's Mischief 起 t=8s | 误锁 **11s** | 误锁 **78s**（+67s） |
| Can We Believe That 起 t=2s | 误锁 143s / 720 拍 | 误锁 58s / 720 拍（此例 hint 反而更好） |

**全曲×全起点扫描（20 曲 × 11 起点 = 220 例）**：hint ON 相对 OFF 误锁**变长的有 43/220 例**，最长 **+67s**，平均 −2.3s。**这是一个真回归**：在中途/冷启动进入强重复段落时，hint 把一次可自愈的错误投票固化成持续误锁。

> 触发条件（现场）：热 cue 起播 / 演出中打开「节拍网格」/ 指纹中断后再识别（`big_gap` 重锚或静音 >10s 复位）/ 曲库扫描中重新识别。**从 t=0 正常起播 20/20 首均正确**（A2 max 3.78），故不是常态路径。

### 3.4 最小修复建议（已验证有效）
**H2：未锁定阶段不发布临时 hint**（只在 `clock.sid==sid` 已锁定时才发 hint；`_beat_pos_grid` 未锁定分支 `_publish_grid_hint(self,-1.0)`）。
`_qa3_fix.py` 实测（模拟该改动的效果）：
- 从 t=0：max **3.78 → 3.65**（不退化）。
- 中途起播：误锁**平均缩短 4.7s**，最长缩短 +73s；最差反例 −21s。
⇒ 方向正确、代价小，**建议采纳**（仍不能 100% 消除冷启动误锁，见 §5）。

> ⚠ 不建议用「投票比阈值回退全局众数」的修法：我验证过它无法区分「hint 正确但弱候选 vs hint 错误」两种情形（两种情形下全局票都高于窗内票），会破坏修法①对重复段落的修复。

## 4. 旧测试 `tools/_grid_m1m2_test.py` M2 断言裁决

- 现状：M1 PASS；M2 第二断言 `abs(pos_gated - pos_ungated) > 100.0` **FAIL**。
- 我独立复核（engine 全链路）：单次强坏窗(+490 拍) → 拍位 **不跳**（206.05，应≈207）；**第二个连续强坏窗** → 跳到 698（已重锚到错坐标）。
- **裁决：新行为正确，旧断言已过时，应当更新。** 理由：旧断言期望「单窗 >100 拍 offset 立即硬重锚」，而这恰是修法②**故意移除**的行为（防孤立强错窗拽飞时钟）。
- **建议改法**（保留 M2 原有「低票不校正」意图，并把「越门槛」期望改成新语义）：
  ```python
  ok = (abs(pos_gated - pos_before) < 2.0) and (abs(pos_ungated - pos_before) < 2.0)
  # 并追加：连续第二个同向强坏窗后，应重锚到错坐标
  ```
  注释写明：>jump_max(32) 拍的单窗不再单帧重锚，需连续 2 窗确认。

## 6. 残留风险（含「测了但没结论」）

- **R1**：本复验的 20 首素材仅前 150s、`bl` 全用缺省 0.5s（用户 config 里 `music_meta` **无 grid**，工程师采集脚本回退默认值）。**beat_len 对「帧—拍」换算有影响**：`HINT_W=32` 帧在更快的曲（160~200BPM）只有 ~2 拍宽，容错更小。建议用**真实 per-song grid** 复跑一次端到端。
- **R2**：`_publish_grid_hint` 每帧写、识别线程每 0.5s 读，逻辑上无撕裂；但**未做端到端进程级压测**（GUI+引擎+音频线程同时跑），仅做了内存级 3 写 3 读 1.5s。
- **R3**：H2 只是「抑制未锁定期 hint」，未解决「已锁定后被 2 个连续强错窗推走」的通路（数据里存在 7 段 ≥2 连续强错窗）。是否需要更硬的「周期性全局探针」需产品定夺。

## 7. 性能 / 线程（补充数据）

- `_beat_pos` 网格路径 **1.66us/次**（关网格 0.47us），每帧多 ~1.2us，60fps 下 ~72us/s，可忽略。
- `_pick` 300 项投票表：无 hint 13.8us / 带 hint 27.3us；`match` 27.5ms 主要花在 SQL/FFT，hint 增量 <0.1%。
- `_publish_grid_hint` 函数体确无锁；识别线程读 `grid_pred_orig` 在 `state.lock` 下。
