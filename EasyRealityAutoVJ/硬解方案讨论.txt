Easy Reality AutoVJ —— 「硬解 / GPU 渲染」可行方案讨论
================================================================================
2026-09-24 21:5x    基于本机实测（16 核 + RTX 3070 Ti）

一、先把一个前提说清楚：**你的素材没法换解码器**
--------------------------------------------------------------------------------
素材库 164 个视频，几乎全是 DXV（DXD3）。DXV 帧内是 DXT 压缩块，而
**NVDEC / QSV / D3D11VA 这些硬件解码器都不支持 DXV**（FFmpeg 里 dxv 只有软件解码）。

所以如果「硬解」指的是「让显卡来解码」，对现有 DXV 素材是**做不到的** ——
除非改素材格式（见第三条的 B / C 路线）。

二、实测数据：CPU 到底花在哪（关键）
--------------------------------------------------------------------------------
[A] 渲染侧（合成/输出），1080p 画布：
    单帧合成 + 颜色 + 后处理（1 个图层）        0.96 ms
    画布→720p 缩放绘制（输出窗口）              0.46 ms
    画布→1080p 绘制                             0.46 ms
    QImage 帧拷贝                               1.34 ms
    颜色 LUT（cv2.LUT, 1080p）                  1.67 ms
    Spout 上传一帧（1080p, CPU buffer）         1.91 ms
    NDI 发一帧（无接收端时）                    ~0 ms

[B] 解码侧（顺序解码吞吐，单文件）：
    分辨率            单帧解码耗时        解码上限
    1920x1080        4.3 ~ 7.6 ms        131 ~ 233 fps
    2048x858         9.05 ms             110 fps
    3840x2160        20.8 ms             48 fps
    5376x1232        16.5 ms             60 fps

结论：**CPU 的绝对大头是解码**，不是合成。
  · 我这是 16 核机器，4K 单层解码就 20.8 ms/帧（上限 48fps）；
    演出常见 4~6 个图层同时解码 → 解码总开销 80~120 ms/帧。
  · 群里那位是 4 核 2.59GHz，同一素材的解码耗时大约要 ×3~4 → 这就解释了 CPU 100%。
  · 相比之下合成只要 1 ms —— **把合成搬到 GPU，收益微乎其微**。

三、真正能省 CPU 的三条路
--------------------------------------------------------------------------------
路线 A：GPU 解 DXT（不转码，最贴合现有素材）
  原理：DXV 帧内就是 DXT1/DXT5（= BC1/BC3）压缩块，而 **GPU 原生支持 BC 纹理** ——
        把压缩块原样上传成 BC 纹理，采样时显卡硬件解压，CPU 完全不参与解压。
  做法：绕开 FFmpeg 解码，用 PyAV 的 `container.demux()` 拿**原始压缩 packet**，
        解析 DXV 头取出 DXT 数据 → `glCompressedTexImage2D(...S3TC_DXT5_EXT)` → 直接采样。
  收益：解码 CPU 占用接近 0；上传数据量只有原来的 1/4~1/6（传压缩块而不是 BGRA）。
  难点：DXV3 有多种子格式（DXT1 / DXT5 / YCG6 / YG10），带 alpha 的素材又是另外的变体，
        要自己写解析器；且纹理必须留在 GPU → 必须配合路线 D（GL 渲染管线）。
  工作量：大。

路线 B：转码成 H.264 / H.265（最快落地）
  用 ffmpeg 批量转成 **H.264 All-I**（每帧都是关键帧，随机 seek 没问题），
  再用 PyAV 走 **NVDEC 硬解** → 解码 CPU 占用接近 0。
  收益：立竿见影，转码脚本一天能写完。
  代价：① 164 个素材要转码一遍（几小时）；
        ② All-I 4K 高码率文件可能比 DXV 还大（可调质量）；
        ③ 硬解出来的帧在 GPU 上，如果还要 CPU 合成，就得下载回内存（比 DXT 解压便宜，但仍有开销）；
        ④ NVDEC 同时解 4K 的路数有限（一般 3~8 路），多图层要实测。

路线 C：转码成 HAP（VJ 圈标准格式）
  HAP 同样是 DXT/BC 封装，但天生按「GPU 直传」设计，有成熟解码路径（不用自己写 DXV 解析）。
  ffmpeg 支持 `-c:v hap` 编码。
  收益同路线 A，难点换成「引入 HAP 解码 + 转码素材」。

路线 D：渲染管线 GPU 化（**与 A/B/C 配套，不是二选一**）
  合成 / 过渡 / 混合 / 颜色 LUT / 后处理全部改成 GL（或 D3D）shader，
  输出直接走 GL 纹理：屏幕显示 + **Spout 用 sendTexture 零拷贝**（省掉现在每次 1.9ms 的上传）。
  只有做到这一步，解码后的帧才能一直留在 GPU，避免「解到显存 → 拷回内存 → 再传回显存」。

四、其他能交给 GPU 的地方
--------------------------------------------------------------------------------
1) 素材扫描 / 导入的特征提取（收益明确、风险低）
   项目里**已经试过 DirectML 加速 Chinese-CLIP，失败了**：
       providers 装上了 DmlExecutionProvider，但推理时
       `Non-zero status code while running Reshape node 'node_view_2'`
   原因是 CLIP 视觉模型是动态 shape，DML 对动态 Reshape 支持差。
   项目根还留着 `_clip_fixed.onnx`（344MB）和 onnxsim —— 当时已经在试着简化模型。
   ⇒ 可行方案：**重新导出固定输入 shape（1×3×224×224）的 CLIP 视觉模型**，
     再用 DirectML EP（Windows 通用，NVIDIA/AMD/Intel 都支持，不用装 CUDA）。
     这个改动**完全不在演出路径上**，不影响稳定性，可以独立先做。

2) 缩略图 / 动态标签扫描
   瓶颈同样是 DXV 解码（跟路线 A 相关）；动态标签的帧差计算本身不慢。
   另外可以「多进程并行」提速，属于治标但立刻可用。

3) 后处理 / 颜色（cv2）
   实测 LUT 1.67ms、后处理 <1ms → 搬 GPU 省不到 2ms，优先级低。

五、建议的落地顺序（风险从低到高，每阶段都能单独上线）
--------------------------------------------------------------------------------
  阶段 0  耗时拆解工具（已完成：tools/frame_cost.py、tools/decode_cost.py）
  阶段 1  CLIP 静态化 + DirectML（导入/扫描提速）          收益中高，风险低
  阶段 2  输出侧 GPU 化：GL 显示 + Spout sendTexture 零拷贝 收益 2~4ms/帧，风险中低
  阶段 3  GPU 合成（图层/过渡/LUT/后处理 shader 化）        收益 1~3ms/帧，风险中高
  阶段 4  GPU 解码（路线 A 自研 DXV-BC，或路线 B 转 H.264） **收益最大**，风险高

  注意：阶段 3 + 4 要一起做才有完整收益（这就是群里说的「相当于重做一遍渲染管线」），
        但可以分阶段推进，随时可停、可回退。

六、在动手之前，有一个「今天就能用」的治标办法
--------------------------------------------------------------------------------
  不改架构、不改代码，直接降低解码负担：
    · 把 4K 素材转成 1080p（解码量降到约 1/4，画质在演出距离下几乎看不出）
    · 控制同时活动的图层数量（每多一层就多一份解码开销）
  这两条能让群友那台老机器立刻不卡。

七、需要你拍板的几个问题
--------------------------------------------------------------------------------
  Q1. 素材能不能接受「转码一次」（决定走路线 A 还是 B/C）？
      A = 不转码，但要我写 DXV 解析器 + 全 GL 管线（工程量大）
      B/C = 先转码，再走硬解（落地快，但要占硬盘/时间，且格式变了）

  Q2. 「硬解模式」你更想要哪个效果？
      · 降低 CPU 占用（让老机器能跑）
      · 提高帧率/上限（能上更高分辨率、更多图层）
      B 和 A 对这些的收益不一样，会决定先做哪块。

  Q3. 硬解要不要做成「另一种渲染管线」，和软解**共用同一套视觉逻辑**？
      建议：两套都要，默认软解；硬解失败自动回退。并且用截图逐像素对比做回归，
      保证「渲染出来的效果和软解基本一样」这条要求能被验证，而不是靠肉眼。

  Q4. 先做阶段 1（CLIP + DirectML，独立、低风险）试试水？
      这个不碰渲染，做完就能看到导入/扫描提速，适合作为第一步。
