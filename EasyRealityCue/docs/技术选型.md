## 0. 一段话结论

**技术栈：Python 3.13 + PySide6-Essentials 6.11.2（界面/自绘时间轴/预览合成）+ PyAV 18.1.0（视频与音频解码、随机 seek、alpha 通道、缩略图取帧）+ numpy 2.5.3（合成与频谱运算）+ onnxruntime 1.30.0 + Beat This! `small0_fixed.onnx`（离线小节/BPM 识别）+ mutagen 1.48.1 或 tinytag（音频标签）+ soundfile 0.14.0（可选，音频重采样读入）+ PyInstaller 6.22.2（打包）。**

**预览合成器走「纯 Qt 光栅路线」**：把各图层画到离屏 `QImage(Format_ARGB32)` 上用 `QPainter::CompositionMode_*` 混合，7 种混合里 6 种 Qt 原生支持，只有 `subtract` 用 numpy 原地饱和减补上。**实测 3 层 1920×1080 合成只要 6~13 ms/帧（77~155 fps），预览窗口尺寸 960×540 只要 2.7 ms/帧** —— 远超「8~15 fps 即可」的要求，**不需要 OpenGL**。

**最大的一个问题（必须找用户拍板）**：PyAV 的 PyPI Windows wheel **硬链接了 GPL-2.0 的 `libx264`/`libx265` DLL**（实测 PE 导入表 + 许可证配置串均可证）。如果本项目要**以 MIT/闭源方式分发**，就必须换掉这一条链路；如果**接受 GPL-3.0 或开源**，则现状可用。详见 §9.1。

## A. 可直接复用的技术

### A1. PySide6 版本 —— 用 **6.11.2（Essentials）**，与参考项目一致

**实测**（`_probe_versions.py`）：

```
PySide6_Essentials     : 6.11.2   | LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only
shiboken6              : 6.11.2   | LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only
PySide6-Addons         : <未安装>
PySide6.__version__ = 6.11.2
QtCore.__version__  = 6.11.2 | qVersion() = 6.11.2
```

- **参考项目用的是 `PySide6_Essentials 6.11.2`**（不是完整 `PySide6`）。本项目只用 `QtCore/QtGui/QtWidgets`，**继续用 Essentials 即可**，比完整 `PySide6`（含 Addons：QtWebEngine/Qt3D/Charts/DataVisualization…）小约 100 MB。
- **许可**：`LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only`。选 **LGPL-3.0** + 动态链接（PyInstaller onedir 天然动态链接）即可闭源分发，只需随包附 LGPL 文本与「可替换 Qt 库」的说明。**无商用限制**。
- **实测确认的兼容坑**：
  1. `PySide6-Essentials` 里**有** `QtMultimedia.pyd`，但**没有多媒体后端插件**，`QMediaPlayer` 实测 `errorString() == 'Not available'`、后端支持的解码格式数 = **0**（见 §2.3）。**不要用它做视频预览**。
  2. `QPainter` 的混合模式只在**光栅设备**（`QImage`）上完整可用。**不要**直接 `QPainter(openGLWidget)` 上叠加混合模式；正确做法是**先合成到离屏 `QImage`，再整幅画到控件**（这正是本报告的推荐路线，AutoVJ 也是这么做的：`engine.py:2857 _compose()`）。
  3. Python 3.13 下 PySide6 6.11 实测可正常 import + 建窗口 + 混合绘制，**无已知阻塞**。
  4. Qt 6 已移除 `QRegExp`（用 `QRegularExpression`）、`exec_()`（用 `exec()`）；`QAction` 在 `QtGui` 而非 `QtWidgets`。移植旧代码时注意。
- **查文档**：Qt 6.11 要求 Windows 10 1809+ / MSVC 2022 运行时（PySide6 wheel 自带 `msvcp140` 等，无需用户装 VC 运行库）。


**结论（实测）**：
- **PyAV 是唯一推荐**：能解 mp4 与 DXV alpha `.mov`，`seek(backward=True)` **11~36 ms**，纯解码 100+ fps。
- **OpenCV 不建议装**：解码能力更弱（DXV 压成 3 通道，**拿不到 alpha**）、seek 慢 4~8 倍（53~180 ms）、体积还多 **97 MB**（`cv2.pyd` 72 MB + 自带 FFmpeg 26 MB）。
- ⚠ **`any_frame=True` 在 mp4 上实测反而慢到 65~819 ms**，且落点不精确 —— **编辑器请统一用 `seek(pts, stream=st, backward=True)`**。
- ⚠ 取帧 API：视频帧用 `frame.to_ndarray(format="bgra"/"rgba")`；**音频帧不能带 `format=` 参数**（实测抛 `TypeError`），直接 `AudioFrame.to_ndarray()`。
- ⚠ **PyAV 的正确打开方式**（AutoVJ 踩过的坑，实测同样适用）：`av.open(path, metadata_errors="replace")`。素材库里大量 GBK 元数据的 `.mov` 不带这个参数会抛 `UnicodeDecodeError`（`media_manager.py:946`）。
- ⚠ **alpha 探测不能只看 `pix_fmt`**：DXV 解码器一律输出 `rgba`，而 DXT1 素材 alpha 全 255。实测 40 个 DXV 里真带 alpha 的只有 2 个 —— 要**实际解几帧看 alpha 是否 <255**（`media_manager.py:871 _av_probe_alpha`，本项目直接复刻）。

### A3. 缩略图生成 —— 视频走 PyAV 取帧 → `QImage` → 缩放 → 存 PNG/JPG

**参考项目做法（`media_manager.py:134 ensure_thumbnail` / `:219 _pick_video_frame` / `:248 _make_av_thumb`）实测可复用**：

| 素材类型 | 路径 | 关键点 |
|---|---|---|
| 图片（png/jpg/webp） | `QImage(path)` → `scaledToWidth(320)` → 存 **PNG** | Qt 读图**支持中文路径**，不要用 cv2 |
| GIF | `QImageReader`，**先 `read()` 跳过头 3 帧**避免黑帧 → 存 PNG | 保留透明通道 |
| 普通视频 | PyAV 采样 **12 个时间点**的帧，按 `std`（内容对比度）打分选最丰富的一帧 | 避开纯黑/纯白过场帧 |
| alpha 视频 | PyAV `to_ndarray("bgra")` → 按 `alpha>16 占比 × 100 + RGB.std` 打分 → `QImage(...Format_ARGB32)` → 存 **PNG** | **必须存 PNG**，JPG 丢 alpha |

**实测性能**：一个 1920×1080 DXV 的「打开容器 + 取首帧 + 转 numpy」= **17~58 ms**；40 个素材全扫 **1.4 s**。

⚠ **铁律（AutoVJ 现场卡死的根因，必须继承）**：**主线程只准读缓存，绝不在 GUI 线程里生成缩略图或探测 alpha**（`ensure_thumbnail` 里顺序解最多 24 帧 + 开容器 + 写盘，164 个素材会让窗口「未响应」）。缺图统一交后台 `QThread` 生成，完成后再刷新。
⚠ 缩略图缓存键 = `md5(path + mtime)`；alpha 视频的真实图是 `.png` 而默认猜 `.jpg`，**取图时必须两个扩展名都试**（`resolve_thumb()`，实测 164 个素材里 49 个 alpha `.mov` 踩过这个坑）。

- **是否要更轻的替代？——不需要，而且更重的替代更差**：
  - `librosa`：受 BSD-ISC 许可，但依赖 `scipy + numba + llvmlite + soxr`，**本机未装**（实测 `<未安装>`），体积与 Python 3.13 兼容性都是额外风险；
  - `madmom`：**GPL-2.0+ 且依赖旧版 numpy/scipy**，Python 3.13 下不可用；
  - `aubio`：**GPL-3.0+**，需要编译，无官方 cp313 wheel；
  - 「纯 numpy 自算 BPM + Beat This 补小节头」这条路**实测 5.05 s/首（180 s 窗）**，比联网/重型栈都可靠，**保持现状**。

#### A5-补. aubio / Essentia 复核（2026-10-04）

> 背景：用户点名要求复核这两个仓库。原 §A5 把 aubio 的否决理由写作「GPL-3.0+」；
> 本项目已定为 **GPL-3.0-or-later**，**该许可理由已不成立** ⇒ 必须换判据重新确认。

**复核方法**：直连 PyPI JSON API 枚举 **全部历史 release** 的 wheel 文件名（不是只看最新版），
并核对官方许可页原文。

| | **aubio** | **Essentia** |
|---|---|---|
| 许可 | GPL-3.0-or-later（`COPYING` 原文核实） | **AGPLv3，仅限非商业**；商业用途须向 UPF/MTG 购买商业许可 |
| 最新版 | 0.4.9（**打包滞后**；仓库本身 2026-04 仍有提交，非停更） | 2.1b6.dev1438（**仍是 beta 版本号**，dev 段 1438） |
| Windows wheel | ❌ **全部 9 个 release 里只有 2 个 Windows wheel**：`cp27-cp27m-win32`、`cp35-cp35m-win_amd64`（约 2015 年）⇒ **cp36 以后无任何 Windows wheel** | ❌ **全部 23 个 release 里 Windows wheel = 0**（只有 `macosx_*` + `manylinux2014_x86_64`） |
| 本机（Win + cp313）可用性 | 须源码编译（MSVC + FFmpeg/libswresample） | 官方文档明写 `pip install essentia` **只覆盖 Linux x86_64/i686** ⇒ 须源码编译（C++ 工具链 + waf） |
| 模型许可 | 无预训练模型 | 预训练模型 **CC BY-NC-ND 4.0**（禁商用 **且禁演绎**），比 Discogs-EffNet 的 CC BY-NC-SA 更严 |

**复核结论：否决结论不变，但判据必须改写。**

1. **aubio 的否决理由从「许可」改为「Windows 分发不可行」**。GPL-3.0+ 与本项目 GPL-3.0-or-later
   **本就兼容**，许可不再是障碍；但「cp36+ 无 Windows wheel」是硬墙 —— 我方要出 PyInstaller
   独立包，不可能要求用户先装 MSVC 编 C 扩展。❌ 不引入。
2. **Essentia 否决理由升级为「许可 + 平台」双否决**。AGPLv3 与 GPL-3.0-or-later 之间并非可直接
   混合（AGPL 的网络分发条款会外溢），且其预训练模型 CC BY-NC-ND **禁商用**；叠加「零 Windows
   wheel」。❌ 不引入。
3. **现有路线无需改动**：`beatgrid.py` + `phrase_bt.py` + `small0_fixed.onnx`（MIT，可商用）
   仍是唯一同时满足**零编译依赖 + 可商用 + 实测跑通**的方案。✅ **保持现状**。
4. ⚠ **aubio 唯一值得记住的点**：它有 `aubio.tempo` **流式** API（实时 BPM/beat 跟随），
   这是 Beat This! 那条离线路线**没有**的能力。**若将来要做「演出中实时跟随节拍」**，
   aubio 是候选 —— 但那时真正的工作量在**自己编译 wheel 并纳入构建流水线**，
   且须重新评估 GPL-3.0+ 在 PyInstaller 冻结包中的分发合规性。**当前不启动。**

## B. 必须新选的部分

### B7. 预览合成器 —— **推荐纯 Qt 光栅路线（QPainter + QImage）**，7 种混合全覆盖

**实测 1：Qt 的 CompositionMode 枚举与真实合成**（`_probe_qt.py`）

`QPainter.CompositionMode` 实测共 **39 个**取值。编辑器需要的 7 种覆盖情况：

| 需求混合 | Qt 取值 | 覆盖 |
|---|---|---|
| normal | `CompositionMode_SourceOver` | ✅ 原生 |
| add | `CompositionMode_Plus` | ✅ 原生 |
| screen | `CompositionMode_Screen` | ✅ 原生 |
| multiply | `CompositionMode_Multiply` | ✅ 原生 |
| lighten | `CompositionMode_Lighten` | ✅ 原生 |
| darken | `CompositionMode_Darken` | ✅ 原生 |
| **subtract** | —— | ❌ **无原生**，用 numpy 原地饱和减 |

**真实合成验证**（目标色 dst=(40,180,90)，源色 src=(200,60,60)，读回中心像素）：

```
CompositionMode_SourceOver -> (200, 60, 60, 255)
CompositionMode_Plus       -> (240, 240, 150, 255)   ← 加性饱和 ✓
CompositionMode_Screen     -> (209, 198, 129, 255)   ✓
CompositionMode_Multiply   -> (31, 42, 21, 255)      ← 40*200/255=31.4 ✓
CompositionMode_Lighten    -> (200, 180, 90, 255)    ✓
CompositionMode_Darken     -> (40, 60, 60, 255)      ✓
位图直读 (BGRA) 可用: True shape (8, 8, 4)   ← QImage.bits() 可直接当 numpy 视图读写
```

**实测 2：合成性能**（`_probe_compose.py`，每层带 opacity 0.85 + crop 源矩形 + 缩放位移）

```
QPainter 合成 1920x1080，3 层：
  SourceOver : 13.1 ms/帧 (p90 14.0) →  76.6 fps
  Plus       :  6.4 ms/帧            → 155.1 fps
  Screen     : 12.0 ms/帧            →  83.3 fps
  Multiply   : 11.2 ms/帧            →  89.4 fps
  Lighten    :  9.7 ms/帧            → 102.7 fps
  Darken     : 10.7 ms/帧            →  93.5 fps

预览窗口尺寸（3 层 Screen）：
  960x540 : 2.74 ms/帧 → 364.9 fps
  640x360 : 1.37 ms/帧 → 728.3 fps
  480x270 : 0.86 ms/帧 → 1161.4 fps

numpy 逐像素（1080p）：
  astype(int16)+clip 饱和减 : 49.6 ms/帧   ← 慢，别用
  原地 255-src + maximum    :  5.8 ms/帧（零拷贝）  ← subtract 用这个
```

**结论（实测）**：

> **推荐路线 (a) 纯 Qt QPainter + QImage 光栅合成，`subtract` 用 numpy 原地补。**
> 理由：① 7 种混合全覆盖，其中 6 种 Qt 原生、1 种 numpy 补（**不是硬伤**）；
> ② 性能**实测 77~155 fps（1080p）/ 365 fps（540p）**，比「8~15 fps」的要求高一个数量级，**没有性能理由上 OpenGL**；
> ③ 纯 CPU、无 GL 上下文/驱动依赖 —— 编辑器是 Authoring 工具，**不播 DXV，也不要求实时**，把「GL 上下文建不起来 / 驱动老旧」这类现场风险彻底排除；
> ④ Qt 的 6 种模式和 AutoVJ 的引擎完全一致，**转场（fade/cut/slide/zoom/glitch）与 crop 的绘制代码可以整套搬**（`engine.py:3008 _draw_layer`：`drawImage(targetRect, img, sourceRect)` 的源矩形重载做裁切，**不做每帧 copy**）。
>
> **不推荐**：
> - **(b) numpy 手写全部混合**：实测朴素饱和减 1080p 要 **49.6 ms/帧**，全手写会明显拖慢；而且等于重新实现 Qt 已经做好且经过验证的显示器色彩/alpha 语义。只把 `subtract` 交给 numpy 是最优分工。
> - **(c) OpenGL / QOpenGLWidget**：性能过剩（现有余量 5~10×），却引入驱动/上下文/线程/打包一连串风险；且 **`QPainter` 的多数 CompositionMode 在 GL 设备上不支持或走回退路径**（**查文档**）。AutoVJ 有 `glctx.py`/`glfw` 那套 GPU 链路，是为**实时演出**服务的，本项目**不需要**。

**实现要点（踩坑预防）**：
1. **合成一律在离屏 `QImage(Format_ARGB32)` 上做**，`QPainter` 用 `SmoothPixmapTransform`，画完再整幅 `drawImage` 到控件 —— 保证混合模式语义正确 + 避免每帧重绘控件。
2. `subtract`：`QImage.bits()` 取 numpy 视图（**改写实测可行**），把 operand 的 alpha 置 0 保护画布 alpha，再 `np.maximum(dst, 255 - src, out=dst)` 或 `cv2.subtract` 原地做（1080p **5.8 ms**）。**LUT / scratch 缓冲按图层缓存复用，绝不在每帧分配**（AutoVJ 实测旧写法 3 层要 264 ms/帧）。
3. `crop` 用 `drawImage(tgt_rect, img, src_rect)` 的源矩形重载，**不要先 `copy()` 再画**。
4. **过渡合成不要在每帧里重建临时图**（AutoVJ 实测每帧 `QImage(W,H)+fill()` = 1.78 ms，`_sub_tmp` 按图层缓存）。
5. 预览**只在界面可见时刷新**，8~15 fps 定时器即可（AutoVJ `CuePreview` 就是 8 fps + `set_active`）。

#### 9.1 ⚠ 最大风险：PyAV 的 wheel 里含 GPL 的 x264/x265

```
  --enable-libx264 --enable-libx265 --enable-nvenc --enable-nvdec --enable-amf --enable-libvpl ...
```

**实测证据 2 —— `avcodec` 的 PE 导入表**（pefile）：

```
IMPORT libx264-165-f3a909470ddc2d85ed21eda3d0fb7954.dll
```

**实测证据 3 —— 进程内确实加载了两者**（`GetModuleHandleA` 全名）：`x264 loaded=True  x265 loaded=True  vpx loaded=True`

**查文档确认**：PyAV 自己的代码是 **BSD-3-Clause**；其 wheel 里 **FFmpeg 核心是 `LGPL-3.0-or-later`**（`--enable-version3`，PyAV 修补了 FFmpeg 的 configure 把 libx264/libx265 移出 GPL 列表），**但 `libx264`/`libx265` 这两个 DLL 本身是 `GPL-2.0-or-later`** —— 无论 FFmpeg 核心怎么标，`pip install av` 仍会把 GPL 代码放进依赖图。

**影响**：
- 若本项目**以 MIT/闭源方式分发 exe** → **不合规**（动态链接 GPL 库构成派生作品，整个发行版需按 GPL 释出）。
- 若本项目**接受 GPL-3.0-or-later（或本就开源）** → **无问题**（GPL-2.0-or-later 与 GPL-3.0 兼容）。
- ⚠ 附带发现：**参考项目 AutoVJ 声明 MIT，但它打包了 PyAV**，存在**同样的合规缺口**（另有 `mutagen` GPLv2）。**仅作提示，我未改动 AutoVJ 任何文件。**

**对策（按推荐度排序）**：
1. **（最简单）把本项目定为 GPL-3.0-or-later 并随后附源码** —— 一次性解决 x264/x265 + mutagen + FFmpeg 的全部问题。
2. **（保 MIT）从 sdist 重建 PyAV 对接一份「无 x264/x265 的 LGPL FFmpeg」**：`pip install av --no-binary av` + 自备 FFmpeg 8.x dev。⚠ **不能简单删 DLL** —— 实测 `avcodec` 把两者写进了**静态 PE 导入表**，删了 `import av` 直接失败。
3. **（保 MIT）不打包 PyAV 的 wheel，改为随包带一个 LGPL 版 `ffmpeg.exe`，用子进程解码**。编辑器是离线/非实时场景，可行；代价是取帧要走进程 IO（预览拖动会钝）。**查文档**：openCV 自带的 `opencv_videoio_ffmpeg4100_64.dll` 实测**不含 `--enable-gpl`、无 libx264**（只有 LGPL），是另一条 LGPL 干净通路 —— 但它**拿不到 alpha**。
4. 仅当项目**确实要闭源且不打算开源**时，才需要走 2/3；**不要**用「删 DLL」「改名」「不声明」这类做法。

| **R5** | **大素材（4K/DXV）+ 多图层预览拖拽** | 拖动播放头掉帧、内存暴涨 | 预览**按窗口尺寸解码/缩放**（`st.codec_context` 侧或 `set_max_size` 缩小后在解码线程转换）；合成在窗口尺寸的离屏图上做（实测 540p 2.7 ms）；配一个「帧缓存 + 上次帧兜底」避免闪烁 |
| **R6** | **seek 落点精度**：PyAV `seek(backward=True)` 落在**关键帧**，非精确帧 | 入点/出点不精确；预览到 ±1 GOP 偏差 | 入出点要精确时：seek 到目标前一个关键帧后**顺序解到目标帧**；或允许「关键帧级」入点并在 UI 标明；`any_frame=True` 在 mp4 上实测**更慢**，别用 |
| **R7** | **打包体积**（不裁剪实测 362 MB） | 分发/下载困难 | 去掉 cv2（−97 MB）+ 写包时跳过未用 Qt DLL（−60~80 MB）→ 约 200 MB 解包 / 120~150 MB zip |
| **R8** | **Qt Multimedia 无后端**（实测 `plugins/multimedia/` 目录不存在、支持格式数 = 0） | 想用 `QMediaPlayer` 做视频预览会**完全不出画面** | **明确不用 QtMultimedia**；预览解码统一 PyAV；若将来要音频试听，走 sounddevice 或另配 Qt 后端 |
| **R9** | Python 3.13 上装更重的 MIR 栈（librosa/numba/madmom/aubio） | wheel 缺失/需要编译/许可（GPL） | **不装**。BPM/小节识别用「numpy 自算 + Beat This! onnx」（实测 5 s/首）。⚠ 2026-10-04 复核：aubio **cp36+ 无 Windows wheel**、Essentia **AGPLv3 且零 Windows wheel**，判据见 §A5-补 |
| **R10** | `.ercue` 内嵌素材导致包体积失控 | zip 几十 MB~几 GB | 沿用设计文档建议：默认**不内嵌**、只给清单；内嵌设上限（建议 500 MB）并给开关 |
